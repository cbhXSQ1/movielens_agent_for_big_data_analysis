## 李丞渊（第 5 节 Agent）记录 2026-09-25

以下 5 条均为本次在 Ubuntu 虚拟机 + Hadoop 3.3.6 伪分布式环境下**真实发生并复现过**的问题，不是推演。

### R1 Hadoop 作业跑成功了，driver 却判它失败

- **现象：** MapReduce 作业在 YARN 上明明跑完（`map 100% reduce 100%`，输出目录有数据），driver 却报 `Job not successful`，整条流水线在中途阶段判定失败。
- **触发条件：** 没有启动 JobHistoryServer（`mapred --daemon start historyserver`）。driver 依赖 HistoryServer 回查作业的最终状态，查不到就按"失败"处理。
- **影响：** 阶段被误判失败 → 后面所有阶段不执行 → 拿不到结果，且容易误以为是清洗逻辑写错了。
- **怎么发现的：** 手动 `yarn application -list -appStates ALL` 看到该 application 状态是 FINISHED，但 driver 日志里查历史状态时报错。
- **证据：** `jps` 只有 5 个进程（缺 JobHistoryServer）；补启后变 6 个，同一条命令重跑即通过。
- **对应作业二：** 这是**"系统各层职责边界"**的现实例子——执行层（YARN）成功 ≠ 编排层（driver）能确认成功。分布式的"成功判定"需要一个可信的状态记录服务，不能靠进程退出码猜。

---

### R2 YARN 容器一启动就被杀，报内存超限

- **现象：** 冒烟测试阶段 Streaming 作业提交后立刻失败，日志提示虚拟内存/物理内存超出限制。
- **触发条件：** `/opt/hadoop` 默认配置里 `yarn-site.xml` 缺内存相关参数、`mapred-site.xml` 缺 map/reduce 的 memory 与 java opts，容器拿到默认下限后撑不住 Python 进程。
- **影响：** 任何作业都跑不起来，卡在第一步，看起来像"代码有 bug"。
- **怎么发现的：** 看 YARN 的 container 日志（不是 driver 日志），里面写的是内存被 kill。
- **证据：** 补了 `yarn-site.xml` 5 项 + `mapred-site.xml` 8 项参数，`stop-yarn.sh` / `start-yarn.sh` 重启后冒烟测试 PASS。
- **对应作业二：** 说明**资源模型必须显式声明**。MapReduce 把"一台机器跑"换成"很多容器跑"之后，内存不再是进程自己争抢，而是由框架按配置分配——配置缺失是分布式系统最常见的失败来源之一。

---

### R3 仓库里的 `hadoop-env.sh` 写死了别人机器的绝对路径（本次最隐蔽的坑）

- **现象：** driver 调 `hdfs dfs` 时报错 `ERROR: JAVA_HOME /home/ubuntu/movielens_agent_for_big_data_analysis/.vendor/jdk-11 does not exist.`，退出码 1。明明 `echo $JAVA_HOME` 是对的。
- **触发条件：** 仓库 `hadoop/conf/hadoop-env.sh` 里直接写死了队长机器上的绝对路径；而 driver 代码又硬编码 `HADOOP_CONF_DIR=<仓库>/hadoop/conf`（`run_task.py` 第 685 / 708 / 1090 / 1101 行）。于是 `hdfs` 启动时会 source 这个文件，把正确的环境变量**覆盖**成不存在的路径。
- **影响：** 所有涉及 HDFS 读写的阶段全部失败，而且报错信息指向 JAVA_HOME，极易误判成"JDK 装错了"，往错误方向查很久。
- **怎么发现的：** 先确认 `echo $JAVA_HOME` 正常、`java -version` 正常，说明不是环境问题；再用 `hdfs dfs -ls /` 单独复现，报错相同 → 锁定是脚本覆盖了变量，而不是系统环境。
- **证据：** 把该文件改成自己机器的路径（并补齐 `log4j.properties`、`configuration.xsl`）后，`hdfs dfs -getmerge ... u_res` 返回 **6946 行**，与 `users.dat` 行数一致，确认修复。另外用软链接 `ln -sfn /usr/lib/jvm/java-11-openjdk-amd64 .vendor/jdk-11`、`ln -sfn /opt/hadoop .vendor/hadoop-3.3.6` 绕开 driver 里硬编码的 `.vendor` 路径。
- **对应作业二：** 这是**"配置与代码分离""环境不可假设"**的硬证据。一份能跑的程序，换个目录就跑不了，说明它把环境假设写进了代码。可移植性是分布式系统的设计目标，不是运气。

### R4 终端里 Ctrl+C 之后，任务状态永远卡在 running 33%

- **现象：** `status.json` 里任务一直显示 `running`、进度 33%，但 `yarn application -list` 返回 0 条——集群上根本没有在跑的作业。
- **触发条件：** 用 `--foreground` 让 driver 前台运行，中途按 Ctrl+C 中断。driver 被杀，但状态文件没被回收，留下一条"僵尸任务"记录。
- **影响：** 后续再提交任务会报 `TASK_ALREADY_RUNNING`；而这条假任务的 `task_id` 又查不到结果（报 `TASK_NOT_FOUND`），整条链路被堵死。
- **怎么发现的：** 状态说在跑，集群说没在跑，两者矛盾 → 判定状态文件是脏的。
- **证据：** 改为异步提交（不加 `--foreground`，driver 用 `Popen(start_new_session=True)` 脱离终端），重跑时加 `--force` 覆盖。
- **对应作业二：** 这是**"状态记录与真实状态不一致"**的典型。分布式系统里"我认为它在跑"和"它真的在跑"是两件事，必须有独立的存活探测（心跳/超时），不能只看本地写下的状态。

> **附：怎么判断任务到底还活着没有（本次实战结论）**
> 1. 不要只看 `status.json` —— 它只在**阶段切换时**才刷新，阶段内部长时间不动是正常的。
> 2. 看集群：`yarn application -list -appStates ALL`，有 RUNNING 就是活着。
> 3. 看进度：HDFS 上对应阶段输出目录的 `_SUCCESS` 文件或文件数量在增长。
> 4. 看日志时间戳：driver 日志最后修改时间一直在变 = 还活着。

### R5 分数从 95.07 涨到 99.95，但脏数据其实没有被"修好"

- **现象：** 综合质量分从 95.07 提升到 99.95（+4.88），看起来清洗效果非常好。但同时：评分记录从 1,150,241 条降到 1,000,209 条，**少了 150,032 条**。
- **触发条件：** 清洗策略里对无法判定的记录采取**隔离（quarantine）**而不是修复，被隔离的数据既不进主表、也不计入评分分母。
- **影响：** 分数上涨有一部分来自"把难题挑出去了"，不完全来自"把问题修好了"。如果只看分数会得出过度乐观的结论。
- **怎么发现的：** 对比数据量变化与分数变化：隔离 100,830 条、去重 49,510 条、修复 13,503 条——修复量远小于移除量。
- **证据：** 本次全量运行结果（`task_id 20260925-184303-379a4b`，9/9 阶段，耗时 10 分 00 秒）：
  - 数据量：评分 1,150,241 → 1,000,209；用户 6,946 → 6,040；电影 4,465 → 3,883
  - 隔离 100,830 条（R2 43885 / R5 12003 / X1 10502 / X2 10502 / P3 7606 / R1 6752 / P2 6075 / R3 3375 / U1 72 / M1 58）
  - 去重 49,510 / 726 / 454；修复 13,503 / 48 / 47 / 73
  - 综合分 95.07 → 99.95
- **对应作业二：** 这是**"指标定义决定结论"**的现实例子，也是课程反复强调的红线：**隔离 ≠ 修复**。任何质量提升的展示，都必须同屏给出数据量变化，否则指标就是可以被"优化"的。另外本次还主动暴露了 4 条 `evidence ≠ detect` 的规则（U2/U3/M8/R9），即"规则说能检出，实际没抓到"，一并写进结果，不做粉饰。
