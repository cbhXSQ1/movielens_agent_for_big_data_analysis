### R1 Hadoop 作业跑成功了，driver 却判它失败

- **现象：** MapReduce 作业在 YARN 上明明跑完（`map 100% reduce 100%`，输出目录有数据），driver 却报 `Job not successful`，整条流水线在中途阶段判定失败。
- **触发条件：** 没有启动 JobHistoryServer（`mapred --daemon start historyserver`）。driver 依赖 HistoryServer 回查作业的最终状态，查不到就按"失败"处理。
- **影响：** 阶段被误判失败 → 后面所有阶段不执行 → 拿不到结果，且容易误以为是清洗逻辑写错了。
- **怎么发现的：** 手动 `yarn application -list -appStates ALL` 看到该 application 状态是 FINISHED，但 driver 日志里查历史状态时报错。
- **证据：** `jps` 只有 5 个进程（缺 JobHistoryServer）；补启后变 6 个，同一条命令重跑即通过。
- **对应作业二：** 这是**"系统各层职责边界"**的现实例子——执行层（YARN）成功 ≠ 编排层（driver）能确认成功。分布式的"成功判定"需要一个可信的状态记录服务，不能靠进程退出码猜。

### R2 YARN 容器一启动就被杀，报内存超限

- **现象：** 冒烟测试阶段 Streaming 作业提交后立刻失败，日志提示虚拟内存/物理内存超出限制。
- **触发条件：** `/opt/hadoop` 默认配置里 `yarn-site.xml` 缺内存相关参数、`mapred-site.xml` 缺 map/reduce 的 memory 与 java opts，容器拿到默认下限后撑不住 Python 进程。
- **影响：** 任何作业都跑不起来，卡在第一步，看起来像"代码有 bug"。
- **怎么发现的：** 看 YARN 的 container 日志（不是 driver 日志），里面写的是内存被 kill。
- **证据：** 补了 `yarn-site.xml` 5 项 + `mapred-site.xml` 8 项参数，`stop-yarn.sh` / `start-yarn.sh` 重启后冒烟测试 PASS。
- **对应作业二：** 说明**资源模型必须显式声明**。MapReduce 把"一台机器跑"换成"很多容器跑"之后，内存不再是进程自己争抢，而是由框架按配置分配——配置缺失是分布式系统最常见的失败来源之一。

### R3 仓库里的 `hadoop-env.sh` 写死了别人机器的绝对路径（本次最隐蔽的坑）

- **现象：** driver 调 `hdfs dfs` 时报错 `ERROR: JAVA_HOME /home/ubuntu/movielens_agent_for_big_data_analysis/.vendor/jdk-11 does not exist.`，退出码 1。明明 `echo $JAVA_HOME` 是对的。
- **触发条件：** 仓库 `hadoop/conf/hadoop-env.sh` 里直接写死了队长机器上的绝对路径；而 driver 代码又硬编码 `HADOOP_CONF_DIR=<仓库>/hadoop/conf`（`run_task.py` 第 685 / 708 / 1090 / 1101 行）。于是 `hdfs` 启动时会 source 这个文件，把正确的环境变量**覆盖**成不存在的路径。
- **影响：** 所有涉及 HDFS 读写的阶段全部失败，而且报错信息指向 JAVA_HOME，极易误判成"JDK 装错了"，往错误方向查很久。
- **怎么发现的：** 先确认 `echo $JAVA_HOME` 正常、`java -version` 正常，说明不是环境问题；再用 `hdfs dfs -ls /` 单独复现，报错相同 → 锁定是脚本覆盖了变量，而不是系统环境。
- **证据：** 把该文件改成自己机器的路径（并补齐 `log4j.properties`、`configuration.xsl`）后，`hdfs dfs -getmerge ... u_res` 返回 **6946 行**，与 `users.dat` 行数一致，确认修复。另外用软链接 `ln -sfn /usr/lib/jvm/java-11-openjdk-amd64 .vendor/jdk-11`、`ln -sfn /opt/hadoop .vendor/hadoop-3.3.6` 绕开 driver 里硬编码的 `.vendor` 路径。
- **对应作业二：** 这是**"配置与代码分离""环境不可假设"**的硬证据。一份能跑的程序，换个目录就跑不了，说明它把环境假设写进了代码。可移植性是分布式系统的设计目标，不是运气。

### R4 终端里 Ctrl+C 之后，任务状态永远卡在 running 33%

- **现象：** `status.json` 里任务一直显示 `running`、进度 33%，但 `yarn application -list` 返回 0 条——集群上根本没有在跑的作业。
- **触发条件：** 用 `--foreground` 让 driver 前台运行，中途按 Ctrl+C 中断。driver 被杀，但状态文件没被回收，留下一条"僵尸任务"记录。
- **影响：** 后续再提交任务会报 `TASK_ALREADY_RUNNING`；而这条假任务的 `task_id` 又查不到结果（报 `TASK_NOT_FOUND`），整条链路被堵死。
- **怎么发现的：** 状态说在跑，集群说没在跑，两者矛盾 → 判定状态文件是脏的。
- **证据：** 改为异步提交（不加 `--foreground`，driver 用 `Popen(start_new_session=True)` 脱离终端），重跑时加 `--force` 覆盖。
- **对应作业二：** 这是**"状态记录与真实状态不一致"**的典型。分布式系统里"我认为它在跑"和"它真的在跑"是两件事，必须有独立的存活探测（心跳/超时），不能只看本地写下的状态。

> **附：怎么判断任务到底还活着没有（本次实战结论）**
> 1. 不要只看 `status.json` —— 它只在**阶段切换时**才刷新，阶段内部长时间不动是正常的。
> 2. 看集群：`yarn application -list -appStates ALL`，有 RUNNING 就是活着。
> 3. 看进度：HDFS 上对应阶段输出目录的 `_SUCCESS` 文件或文件数量在增长。
> 4. 看日志时间戳：driver 日志最后修改时间一直在变 = 还活着。

### R5 分数从 95.07 涨到 99.95，但脏数据其实没有被"修好"

- **现象：** 综合质量分从 95.07 提升到 99.95（+4.88），看起来清洗效果非常好。但同时：评分记录从 1,150,241 条降到 1,000,209 条，**少了 150,032 条**。
- **触发条件：** 清洗策略里对无法判定的记录采取**隔离（quarantine）**而不是修复，被隔离的数据既不进主表、也不计入评分分母。
- **影响：** 分数上涨有一部分来自"把难题挑出去了"，不完全来自"把问题修好了"。如果只看分数会得出过度乐观的结论。
- **怎么发现的：** 对比数据量变化与分数变化：隔离 100,830 条、去重 49,510 条、修复 13,503 条——修复量远小于移除量。
- **证据：** 本次全量运行结果（`task_id 20260925-184303-379a4b`，9/9 阶段，耗时 10 分 00 秒）：
  - 数据量：评分 1,150,241 → 1,000,209；用户 6,946 → 6,040；电影 4,465 → 3,883
  - 隔离 100,830 条（R2 43885 / R5 12003 / X1 10502 / X2 10502 / P3 7606 / R1 6752 / P2 6075 / R3 3375 / U1 72 / M1 58）
  - 去重 49,510 / 726 / 454；修复 13,503 / 48 / 47 / 73
  - 综合分 95.07 → 99.95
- **对应作业二：** 这是**"指标定义决定结论"**的现实例子，也是课程反复强调的红线：**隔离 ≠ 修复**。任何质量提升的展示，都必须同屏给出数据量变化，否则指标就是可以被"优化"的。另外本次还主动暴露了 4 条 `evidence ≠ detect` 的规则（U2/U3/M8/R9），即"规则说能检出，实际没抓到"，一并写进结果，不做粉饰。

### R6 追问时运行口径丢失：「页面上选的」和「实际跑的」不一致

- **现象：** 页面选「本地引擎」发起任务，然后在追问框问"跑到哪一步了"，driver 实际收到的是**默认的集群口径**。
- **触发条件：** 前端追问入口 `frontend/js/app.js:1202` 硬编码传 `null`（首轮 `:1060` 传的是对的）→ `api.js:162` 不写入 body → 后端 `exec_mode=None` → `driver_client.py:111-112` 丢弃 None → driver 回落 `cluster`。
- **影响：** 用户在界面上做的选择被静默丢弃；且因为默认值恰好等于页面默认选项，大多数情况下不显形，**只在显式选了「本地引擎」后才暴露**——这是最危险的一类 bug。
- **怎么发现的：** 前端同学反馈后，沿 `app.js → api.js → http_api.py → agent.py → tools.py → driver_client.py` 逐层核对参数透传，定位到传 null 的那一行。
- **证据：** `app.js:1060`（首轮，正确）与 `app.js:1202`（追问，传 null）对比。
- **修复：** 后端按 **task_id** 记住该轮真实生效的口径（新增 `agent/session.py`）。选这个方案的理由是：追问本来就带 task_id，**零前端改动即可修好**，且不引入 session 概念；进程重启后回落默认值（失效方向安全）。同时把生效口径放进返回体 `opts` 回显，前端想显式回传随时可用。
- **对应作业二：** 「**有状态服务 vs 无状态服务**」的现实例子。HTTP 本身无状态，但"用户这一轮选了什么"是跨请求的状态——要么让客户端每次重传（容易漏），要么服务端按某个键记住它（要有键、要有失效策略）。

### R9 `use_default` 是个死参数（解析出来了但没人读）

- **现象：** `intent.py:134-135` 会解析出 `params["use_default"] = True`，但 `agent.py` 里**从来没有读过它**。
- **触发条件：** 用户说"用默认规则清洗"，这个偏好被解析出来后被丢弃。
- **影响：** 功能上无害（本来就用默认），但代码里存在一个"看起来实现了、实际没生效"的参数——**评审时一眼能看出是没做完**。
- **怎么发现的：** 全仓库搜 `use_default`，只有写入处没有读取处。
- **修复：** 不删也不留注释，改成**「默认方案自检开关」**：用户明说"用默认规则"时，先在发起前真跑一次 `tools.validate_config()`，过不了就**不发起任务**并如实报错。既让参数活了，又把「配置只读 + 不编造」讲圆了。
- **对应作业二：** **"声明式配置的信任问题"**。用户说"用默认配置"，系统不能假设它一定合法，要先自检——自检失败就停下，而不是带着一个坏配置跑下去再报一堆看不懂的错。

### R10 大模型护栏的一个隐蔽实现 bug：占位符里的数字被误判

- **现象：** 润色功能"配了但永远不生效"。
- **触发条件：** 第三层校验用正则查"输出里有没有新数字"，但占位符 `{v0}` 里的 **`0` 本身就是数字**，被当成新数字 → **所有正常润色都被误判丢弃**。
- **影响：** 润色 100% 失效，而且不报错（只是走"丢弃润色、返回原句"这条安全路径），**很难察觉**。
- **怎么发现的：** 写假 LLM 自测时，先写了"断言返回值不含占位符"——这个断言在原句上也成立，是**假阳性**；改成"断言文本确实变了"才暴露出来。
- **证据：** 修正前 `polish()` 恒返回原句且原因恒为"出现未 mask 的数字"；修正后先剥掉合法占位符再查数字，正常润色才真正生效。
- **修复：** `_PLACEHOLDER_RE.sub("", got)` 之后再查数字。
- **对应作业二/三：** **"校验规则本身也会有 bug，而且它坏的方向往往是'过度拦截'"**。安全校验失效通常表现为系统变哑而不是变错，所以**必须有一条"正常路径确实生效"的正向断言**，不能只测拦截。

### R11 `llm.supported` 恒为 true，「默认不存在」这条承诺落空

- **现象：** `/health` 里 `llm.supported` 永远是 `true`，导致"未配置时隐藏设置入口"永远不成立，页面上一直有个大模型齿轮。
- **触发条件：** 实现写的是 `supported = (cfg is not None)`，而 `cfg` 来自 `llm_config.load()`，**它永不返回 None**（最坏返回一个 `enabled=False` 的实例）。只要代码里有这个模块，就恒为真。
- **影响：** 我自己在前端清单里写的验收第 7 条（"未配置时齿轮 hidden"）**永远过不了**——文档和代码打架，属于自己打自己脸。
- **怎么发现的：** 第 6 节同学逐行读我的 `_load_llm_config()` 和 `load()` 核出来的，不是跑出来的。
- **修复：** 引入**后端总开关** `AGENT_LLM_SUPPORTED`（默认关）。`supported` 读它，`usable` 也把 `supported` 算进去（变成五项齐全）。并且**剔除请求里的 `supported` 字段**——前端面板不能替后端开这个开关，否则"默认关闭"形同虚设。
- **对应作业二：** **"能力声明"和"能力启用"是两件事**。一个模块存在 ≠ 这个功能被启用。把"存在性"当"可用性"暴露给调用方，是所有可选特性最常见的翻车方式。
- **后续口径调整（2026-09-29 晚，与第 6 节商定）：** 修完 R11 后前端同学反馈"未配置就整块隐藏"不合理（① 用户看到绑了 API 却没法操作 ② 有无功能两套布局难维护）。定为：**入口（齿轮）常显**，`supported=false` 时点开面板给一句提示「后端未开启大模型增强：启动时设置 `AGENT_LLM_SUPPORTED=1`」。**后端逻辑不变**，只改前端呈现与文档。

### R12 「按置信度决定是否问大模型」是个死条件

- **现象：** `fallback` 模式下，除了彻底听不懂（`unknown`），**任何正常提问都不会触发大模型**——汇报现场看不出接了 LLM。
- **触发条件：** 判断写的是 `confidence < 0.5`，但规则解析的置信度算法是 `0.5 + 0.15 × 命中词数`，**只要不是 unknown 就恒 ≥0.5**，这个条件永不成立。
- **影响：** 功能"配了但永远不生效"，而且**不报错**（静默走规则路径），极难察觉。
- **怎么发现的：** 第 6 节同学提出"面板没有 mode 字段"；我顺着查，发现比他说的更严重——阈值本身就是死的。
- **修复过程（值得记）：** 第一反应是把阈值调到 0.8，实测**还是不行**：常用说法置信度落在 0.80~0.85，0.80 不小于 0.8，照样卡在边界上。所以调阈值是在一个死思路上打补丁。最终**放弃阈值**，把 `fallback` 语义写死成"只在 unknown 时兜底"，另用 `mode=always` 满足演示需求。
- **对应作业二/三：** **"降级策略的触发条件必须能被真实触发"**。写了一个看起来精细的触发条件，结果它在业务数据分布下永不成立——策略就退化成了摆设。判断条件要拿真实数据跑一遍，不能只看公式合理。

### R13 请求体不是 UTF-8 时，服务端直接崩且返回空响应

- **现象：** Git Bash 里 `curl -d '{"text":"今天天气怎么样"}'` 打过去，客户端**什么都收不到**（既不是 JSON 也不是报错），服务窗口刷 `UnicodeDecodeError: can't decode byte 0xbd in position 9`。
- **触发条件：** 中文 Windows 上，Git Bash 的 `curl` 按系统本地编码（**GBK**）发请求体；"今"的 GBK 是 `0xbd 0xf1`，服务端 `http_api.py:129` 硬按 UTF-8 解码 → 抛异常。
- **影响：** 异常发生在 `do_POST` 开头，响应头都还没发，`BaseHTTPRequestHandler` 直接断连 → **客户端拿到空响应**。表现就是"命令跑完啥都没有"，极难排障（同一时刻 `/health`、`/api/llm/test` 都正常，因为它们请求体是 `{}` 不含中文）。
- **怎么发现的：** 先在服务窗口看到 traceback，才定位到是编码问题而不是逻辑问题。
- **修复（两处）：**
  1. `_decode_body()`：UTF-8 → GBK → 坏字节替换，三级容错，**永不抛异常**。GBK 也能正确解出中文，所以命令行里发中文照样能用。
  2. 覆盖 `handle_one_request()`：任何未捕获异常都返回 `500 + INTERNAL_ERROR` 的 **JSON 信封**，不再返回空响应。
- **顺带修的**：`MAX_TIMEOUT` 从 5 秒放宽到 30 秒（本地 7B 模型生成 200 token 要 10~20 秒，5 秒根本不够）。
- **对应作业二：** **"服务端必须能承受非法输入"**。协议规定客户端该发 UTF-8，但现实里客户端不一定守规矩；一个请求体编码不对就让整个服务返回空响应，是典型的**输入校验缺失**。而且"失败时给真实原因"是我们自己的红线——空响应连原因都不给，比报错更糟。
