# 迭代二 · Hadoop 端侧 MCP 开发要求

> 交付对象：**虚拟机（Hadoop）端开发**。
> 目的：把 Hadoop 侧的数据治理能力以 **MCP（Model Context Protocol）** 形式对外提供，供宿主机上的 Agent 调用。
> 本文是**端侧开发的完整要求**，自包含；细节字段以下文为准，Agent 侧配套文档见 `docs/agent/Agent_接口文档.md`（§3 前端↔Agent、§5 Agent↔Hadoop MCP）。
> 总原则：**能力上与既有数据处理程序一一对应、只加不减；错误语义无损；长任务可被唤醒；可发现、可取证；对外只做加性变更。**

---

## 1. 目标与边界

- 在虚拟机里运行一个 **MCP Server**，把现有数据治理能力（校验、清洗、评分、发布、查询产物等）暴露为 MCP **工具**与**资源**。
- 宿主机上的 Agent 通过网络调用该 MCP Server；Agent 侧不再与 Hadoop 同机。
- 本次**只做 Hadoop 端**；Agent、前端由另两方分别负责（本文件是契约）。
- Hadoop 端**必须自校验**（依赖、互斥、版本），不能只依赖 Agent 侧策略层拦截。

## 2. 总体架构

```
宿主机：前端 ── HTTP/SSE ──► Agent（LLM 主控 / 离线直调）
                                 │  MCP（网络）
                                 ▼
虚拟机：MCP Server ── 调用 ──► 现有「数据处理程序」（driver + Hadoop 作业链）
                                 └── HDFS：原始区 / 清洗产物 / 发布区
```

- MCP 工具的执行体，对应现有的 **driver 子命令**（见 §17）。
- 现有 driver 的「一次请求 → 一个 JSON 信封」结构，天然对应 MCP 的「调用工具 → 返回内容」；**建议直接把每个子命令包成一个 MCP 工具**。

## 3. 工具清单

### 3.1 与既有能力一一对应（必备）

| MCP 工具 | 对应能力 | 说明 |
|---|---|---|
| `validate_config` | 校验配置 | 校验清洗/评分方案是否合法，不改数据 |
| `list_schemes` | 列方案 | 列出已登记的清洗/评分方案 |
| `start_cleaning_task` | 发起全流程 | 清洗 + 前后评分 + 发布，**异步**返回任务编号 |
| `start_clean_task` | 只清洗 | 仅清洗链，不评分、不发布 |
| `score_task` | 独立评分 | 对原始数据 / 指定任务产物 / 已发布数据评分 |
| `get_task_status` | 查状态 | 任务进度与阶段（**运行中要能反映真实进度**） |
| `get_task_result` | 取结果 | 权威结果信封 |
| `get_samples` | 取样例 | 清洗后样本 / 隔离区样本（带规则与原因） |
| `get_report` | 取报告 | 结构化 report.json / 全文 report.md |
| `list_tasks` | 列任务 | 历史任务列表 |

### 3.2 取证 / 自描述类（新增，必备）

| MCP 工具 | 说明 |
|---|---|
| `list_published_versions` | 列发布区里的数据版本（供「资源」页） |
| `list_task_files` | 列某任务目录下的产物文件（相对路径 / 大小 / 类型） |
| `read_task_file` | 读某任务产物的内容（文本/JSON/Markdown；大小受限） |
| `get_job_counters` | 取作业计数器（隔离/去重/修复等对账数字） |
| `get_job_logs` | 取作业日志片段（排障用） |
| `describe_capabilities` | **能力自描述**：返回工具清单（名称、说明、参数、来源、是否长耗时、预计时长）与契约版本 |

> `describe_capabilities` 是 Agent「工具表」的权威来源；工具集合变化时，Agent 会据此刷新。

### 3.3 每个工具的输入/输出（关键字段）

- **输入**：参数以 JSON Schema 描述；枚举、默认值、是否必填要与 driver 口径一致（见 §5）。
- **输出**：统一为「信封信封」JSON（见 §6），成功 `ok=true` + 业务字段；失败 `ok=false` + `error{code,message,...}`。
- **长耗时工具**：在 `describe_capabilities` 里标注 `long_running=true` 与 `estimated_seconds`（见 §7）。

## 4. 参数要求（不得收窄）

各工具应暴露 driver **全部**有意义的参数，至少包括：

- **范围**：`scope` = `full`（默认，正式口径）/ `sample`（前 2000 行，仅联调）。
- **执行方式**：`exec_mode` = `cluster`。
- **任务类型**：`task_type` = `full` / `clean`。
- **数据版本**：`data_version`（与配置声明不一致 → `VERSION_CONFLICT`）。
- **自定义方案**：`rules`（清洗规则路径）、`scoring`（评分方案路径）；**必须先 `validate_config` 再执行**，校验结果结构化返回。
- **幂等/强制**：`force`（忽略「已有运行中任务」冲突）。
- **标签**：`tag`。
- **评分来源**：`source` = `raw` / `published` / `task`，`source=task` 需 `from_task`。

## 5. 参数与配置的边界（红线）

- 自定义方案支持「先校验再执行」；校验失败**不得**带着坏配置运行。
- `data_version`、清洗规则版本、评分方案版本、时间边界 **四者成组**出现，不得跨版本混用。
- 时间边界 `T1`（训练期截止）/ `T2`（验证期截止）由第一轮统一确定，随结果返回。

## 6. 返回信封与可观测

所有工具返回统一信封（成功示例）：

```json
{
  "ok": true,
  "interface_version": "1.0",
  "task_id": "20260930-004132-d7ae13",
  "status": "running | succeeded | failed",
  "stage": "clean_users", "stage_index": 3, "stage_total": 9,
  "progress_percent": 33,
  "started_at": "2026-09-30T00:41:32Z", "updated_at": "…",
  "counts": { "input": {...}, "output": {...}, "quarantine": {...}, "dedupe": {...}, "fix": {...} },
  "scores": { "before": {...}, "after": {...}, "delta": {...} },
  "versions": { "data": "ml1m-clean-v1", "rule": "1.0.0", "scoring": "1.0.0" },
  "time_boundaries": { "T1": "2001-12-31T23:59:59Z", "T2": "2002-06-30T23:59:59Z" },
  "artifacts": [ { "id": "...", "title": "report.md", "category": "报告",
                   "kind": "md", "path": "report.md", "size": 4421 } ],
  "errors": []
}
```

要求：
- **长任务返回预计时长**（`estimated_seconds`），供 Agent 挂起展示。
- **错误语义无损**（见 §9），保留类别 + 原因 + 补救提示。
- 产物的**结构化位置信息**（任务编号 + 相对路径 + 类型），供前端「结果/文件」板块直接渲染。
- **不产生、不编造任何业务数字**；数字只能来自真实作业结果。

## 7. 长任务与完成通知

- `start_*` 发起后**立即返回**任务编号与「已受理」状态（异步）。
- `get_task_status` **运行中必须反映真实进度**（阶段、百分比），不能长期停在 0。
- **完成通知/订阅（强烈建议）**：提供 MCP 通知（或可订阅的完成事件），让 Agent 能在任务完成时被唤醒；**若不提供，则退化为 Agent 定期查询到终态**——但**中断信号始终由 Agent 侧发出**。
- **支持取消/中止**（即使现在不用，也请留接口）。

## 8. 前置依赖与并发

| 操作 | 前置依赖 | 互斥/并行 |
|---|---|---|
| 发起全流程 / 只清洗 / 评分(raw) | 原始数据可读 | **占用任务锁（串行）** |
| 评分(task) | 目标任务 succeeded 且 cleaned 存在 | 占用任务锁 |
| 评分(published) | 发布区存在 | 占用任务锁 |
| 发布 | finalize 产物存在 | **发布互斥 + 版本哈希保护** |
| 读命令（status/result/samples/report/tasks/schemes/文件） | 无 | 只读，可并行 |

- 依赖不满足 → 结构化错误 `DEPENDENCY_MISSING`，信息里写清**缺什么**（哪个任务、哪份产物）。
- 已有任务在跑 → `TASK_ALREADY_RUNNING`，并给出**占用者**与**如何解除**。
- 暴露锁/队列状态，便于 Agent 解释与用户操作。

## 9. 错误码映射（不得丢语义）

现有的**退出码**与**传输错误**必须映射为**结构化错误码**：

| 现有退出码 | 含义 | 映射后的错误码 |
|---|---|---|
| 0 | 成功 | 无错误 |
| 2 | 参数非法 | `USAGE` |
| 3 | 任务失败 | `TASK_FAILED` |
| 4 | 不存在 | `TASK_NOT_FOUND` |
| 5 | 未完成 | `TASK_NOT_FINISHED` |
| 6 | 版本冲突 | `VERSION_CONFLICT` |
| 传输 | 无输出 / 非法输出 / 不可达 / 超时 | `DRIVER_NO_OUTPUT` / `DRIVER_BAD_OUTPUT` / `DRIVER_UNREACHABLE` / `DRIVER_TIMEOUT` |

新增：前置依赖缺失 → `DEPENDENCY_MISSING`；已有任务在跑 → `TASK_ALREADY_RUNNING`；配置非法 → `CONFIG_INVALID`（保留 driver 原码）。

> 映射要求：已是结构化码的一律原样保留，**不得降级**成通用码；仅有退出码可依时才按上表映射，并把原码记入 `driver_code` 保留。

## 10. 发现与版本协商

- 工具表每条含：**名称、说明、参数与默认值、来源、是否长耗时、预计时长**。
- MCP 契约带 **`interface_version`**；Agent 据其判断能力可用性。
- 对外**只做加性变更**；字段语义变更必须升版本并同步双方。

## 11. 只读资源（MCP resources，建议）

用 MCP 的「资源」能力暴露只读产物，让 Agent 按需取用、不必为每种产物单开工具：

- 已发布数据版本、清洗产物、隔离样例、报告、配置（清洗规则 / 评分方案）。

## 12. 资源 / 文件接口（Hadoop 接管后需提供）

Agent 侧目前已用**本地文件系统**实现了「资源与文件」的直通接口（`docs/agent/Agent_接口文档.md` §3.11）。当 Hadoop 侧接管后，**对外形状不变**、实现改由 Hadoop 侧执行。Hadoop 端需要提供等价能力：

| 能力 | 说明 |
|---|---|
| **原始数据上传** | 上传 `.dat` / `.zip`（三表：ratings/users/movies）到 Hadoop 原始区（HDFS） |
| 列原始数据 | 列出原始区的数据集/文件 |
| 列已发布数据 | 列出发布区 `data_version`（含来源任务、表、时间） |
| 列方案 | 列已登记的清洗规则 / 评分方案 |
| 取方案内容 | 返回方案完整 JSON（供「评分依据」） |
| 上传方案 | 上传 `.json` 方案并校验 |
| 列任务产出文件 | 列某任务目录下文件（相对路径 / 大小 / 类型） |
| 读文件内容 / 下载 | 文本/JSON/Markdown 预览（大小受限）+ 下载 |

## 13. 数据 / 版本 / 时间边界契约

- **发布不可覆盖**：已发布数据不许原地改动，只能以**新数据版本**演进；发布前与权威哈希清单比对（内容同→幂等放行；同版本不同内容→`VERSION_CONFLICT` 拒绝）。
- **目录布局是下游契约**：`cleaned/<数据版本>/<table>.dat`、隔离区、报告、指标等；布局变更只通过新数据版本实现。
- **血缘**：每个产物带它使用的数据版本、规则版本、评分版本、时间边界。

## 14. 传输与可用性

- **网络形式**：宿主机能连到虚拟机上的 MCP Server（选可用于「宿主机 ↔ 虚拟机」的传输；Hadoop 的几个 Web UI 只绑 localhost 的历史问题与此无关，但要保证 MCP Server 的端口对宿主机可达）。
- **基本访问控制** + **健康检查**（可查询 Server 存活/版本）。
- 超时/不可达要能被 Agent 归类（见 §9）。

## 15. 安全约束（明确不做）

- **不给 Agent 开放「执行任意命令」的口子**；破坏性操作要有确认与护栏。
- 只读资源与写工具分离；写工具受任务锁与版本保护约束。

## 16. 兼容与演进

- Hadoop 端与 Agent 端各自演进时，**对外契约只做加性变更**。
- 若确需变更字段语义，**先升 `interface_version` 并同步双方**，不允许悄悄改字段。

## 17. 现有可复用资产（迭代一已有）

- 现有 **driver 子命令**（即 §3.1 的能力来源）：`validate` / `schemes` / `start`（`--task-type full|clean`、`--scope full|sample`、`--exec`）/ `score`（`--source raw|published|task`）/ `status` / `result` / `samples` / `report` / `tasks`，以及枚举/默认值口径。
- **任务产物目录**：`var/tasks/<任务号>/`（`status.json` / `result.json` / `counts.json` / `stats.json` / `report.md` / `report.json` / `metrics/` / `cleaned/<版本>/` / `quarantine/<版本>/`）。
- **发布区**：HDFS `/data/published/<数据版本>/` + 权威哈希清单。
- 清洗规则 / 评分方案：`config/cleaning_rules.v1.json`、`config/scoring_scheme.v1.json`。
- 现有脚本：集群启停、上传原始数据、提交作业等（见 `docs/hadoop/runbook.md`）。
- **driver 的「一次请求 → 一个 JSON 信封」结构**就是 MCP 工具的天然执行体。

## 18. 验收标准（VM 侧自测）

1. **工具齐全**：§3.1 + §3.2 的工具都能被 `describe_capabilities` 列出，参数与 driver 口径一致。
2. **往返正确**：用宿主机 Agent（或 MCP 客户端）真实调用每个工具，成功/失败信封符合 §6/§9。
3. **进度真实**：运行中任务经 `get_task_status` 能看到阶段推进（不是长期 0）。
4. **依赖与互斥**：缺数据/缺产物 → `DEPENDENCY_MISSING`；已有任务在跑 → `TASK_ALREADY_RUNNING` 且给出占用者与解除方式。
5. **版本保护**：同版本不同内容发布 → `VERSION_CONFLICT`；同版本同内容 → 幂等放行。
6. **长任务**：完成后能被 Agent 唤醒（或至少状态可查到终态）；支持取消。
7. **资源**：原始数据上传、已发布列举、任务产物列举/读取/下载可用。
8. **只读资源**：MCP resources 可列出并读取。
9. **网络与健康**：宿主机可达，健康检查可用。

> 与迭代一纪律一致：**不得用占位数据、示例结果或主观推测代替真实运行结果**；失败要如实说明失败环节与原因。

## 19. 明确不做（本次）

- 不在 Hadoop 端实现 Agent 的编排、意图解析或前端展示。
- 不开放任意命令执行。
- 不重复实现 Agent 侧的护栏/数字溯源（那是 Agent 侧职责）——但**状态判定与失败判定要以执行侧为准**（见 §7）。

## 21. 本轮确认的调整（2026-10-17）

> 本节记录实现前确认的六项决定。**正文保留原样**，便于对照：与本文件不同处，以本节为准。
> 详细方案见 `docs/hadoop/迭代二_MCP_实现方案.md`。

| 项 | 本文件原写法 | 本轮决定 |
|---|---|---|
| 原始数据上传（§12） | Hadoop 端需提供"原始数据上传"的等价能力，保持对外形状不变 | **不对外提供上传能力**：Agent 对数据只有查看权，不持有、不改写。运维上传沿用现有本机脚本（`hadoop/scripts/upload_raw.sh`，已承担打包、物化行号、上传三件事）。前端"资源"页的上传入口随之取消 |
| 取消/中止（§7、§8） | "支持取消/中止（即使现在不用，也请留接口）" | **要求真正实现**：后台作业按独立进程组启动，可定位后发出终止信号；并**新增"已中止"状态**，否则任务会永久停在运行中、把占用挂住。状态写入的这一处是本次唯一改动既有业务的地方 |
| 状态取值（§6、§7） | `running / succeeded / failed`（另有 queued） | **加性新增** `aborted`（已中止）。对端接口文档 §3.8 已有"已中止"，属对齐而非新造 |
| 错误码（§9） | 列出退出码映射与三项新增 | 另**加性新增**四条只读类错误：文件不存在、路径越界、内容过大、不可预览；命名**沿用对端接口文档 §3.11.5 的既有名称**，避免两端各说一套。原本的"不支持的文件类型""上传过大"随上传关闭一并取消 |
| 传输与可用性（§14） | "选可用于宿主机 ↔ 虚拟机的传输" | 服务以网络方式常驻，**监听所有网络接口**，端口 **8765**，带访问口令；**宿主机侧需加一条端口转发**（宿主机本机 8765 → 虚拟机 8765）—— 本机走默认地址转换模式，宿主机不能主动连入，不加转发则连不上 |
| 完成通知（§7） | "强烈建议提供 MCP 通知" | 实现为**阻塞式等待工具**（挂起到终态或超时，超时回"仍在运行"）+ 状态查询；**不做服务端主动推送**。中断的发出者仍是 Agent 侧 |

另：契约版本沿用对端占位中的 `1.0` 作为本端第一版，不另起新号；后续只做加性变更时再升。

## 22. 追加要求（2026-10-18）：自定义方案上传

> 背景：现有能力只能「列方案 / 取方案内容 / 校验方案」，方案必须是**虚拟机配置目录里已存在的文件**（`rules`/`scoring` 传的是方案**文件名**，由本端驱动读配置目录）。用户在前端上传的自定义清洗/评分方案因此无处落地、无法用于校验与发起任务。用户对「自定义方案」的需求较高，需要一个**上传入口**。请本端新增这一能力。

### 22.1 形态（二选一，建议前者）

- **新增 MCP 工具 `upload_scheme`**（推荐：与现有工具同一套调用/信封/鉴权，`describe_capabilities` 自动可见）；或
- 新增一条带口令的写路由（如 `POST /schemes`），鉴权与两段下载路由同一套口令。

### 22.2 输入

| 参数 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 目标文件名：**单层文件名**、以 `.json` 结尾（如 `my_rules.v2.json`）；**不得含路径分隔符** |
| `content` | 是 | 方案的 JSON 内容（文本） |
| `type` | 否 | `cleaning_rules` / `scoring_scheme`；缺省由内容判定 |
| `overwrite` | 否 | 同名已存在时是否覆盖，缺省 `false` |

### 22.3 行为

- **先校验后落盘**：做与 `validate_config` 同等的校验；**不通过则不写入**，并把校验结论原样返回。
- 通过后写入**与现有方案同一目录、同一命名规则**（`config/` 下）。
- 同名已存在：缺省**拒绝**并提示；显式 `overwrite=true` 才覆盖。
- 返回：登记结果（文件名、类型、校验摘要），字段与 `list_schemes` 的条目对齐，便于前端直接刷新。

### 22.4 错误语义（复用现有码，语义无损）

- 文件名非法 / 含路径分隔符 → `USAGE`（或 `FORBIDDEN_PATH`，与本端既有判定一致即可）；
- 内容不是合法 JSON，或方案校验不通过 → `CONFIG_INVALID`（附明细）；
- 内容过大 → `CONTENT_TOO_LARGE`；
- 同名冲突且未允许覆盖 → `VERSION_CONFLICT`（或明确的专用码，需在能力自描述里列出）；
- 未带口令 / 口令错误 → `UNAUTHORIZED`。

### 22.5 安全

- 需口令；**限制文件名**（单层、`.json`）；**限制大小**；**禁止路径穿越**；写入目标不得越出方案配置根。

### 22.6 契约

- **加性变更，不升版本**（仍为 `1.0`）；新能力出现在 `describe_capabilities` 的工具清单里。

### 22.7 对端（Agent / 前端）如何接

- 前端**保留上传入口**；上传 → Agent 带口令转发 → 成功后刷新远端方案列表（本端能力就绪后由 Agent 侧接上）。
- 在本能力可用之前，Agent 侧的上传暂为**本机暂存**，界面会标注；待本能力上线后切换到远端。

### 22.8 验收

1. 上传一个合法方案 → `list_schemes` 能看到它；
2. `get_scheme_content` 取回的内容与上传一致；
3. 该方案能通过 `validate_config`；
4. `start_cleaning_task` / `score_task` 可用该方案名发起；
5. 非法文件名 / 非法内容 / 超限 / 无口令，分别返回对应错误码，且**失败时不留半成品文件**。

## 23. §22 的实现说明（本端已完成，2026-10-18）

> 记录实现时的取舍，供三方对齐；与 §22 冲突处以本节为准。

| 项 | 决定 | 理由 |
|---|---|---|
| 形态 | 采用**新增工具 `upload_scheme`**（§22.1 的首选项） | 与现有能力同一套调用、信封、鉴权，能力自描述里自动可见，对端不必再接一条新通道 |
| 同名冲突的结论 | 新增专用码 **`SCHEME_EXISTS`**（已进对外错误码清单） | 版本冲突码在本端语义里指"同一数据版本装进了不同内容"，用它会把人引去升数据版本；而这里只要换名字或允许覆盖 |
| 校验方式 | 先写**隐藏临时文件**（故意不带 `.json` 后缀），用与「校验方案」同一条通路做**成对**校验，通过后原子替换 | 两个考虑：临时文件不带 `.json` 就不会在"列方案"里露出半成品；成对校验是因为校验器本来就要求"规则 + 评分"两份一起看 |
| 默认方案保护 | **两份随仓库交付的默认方案一律不许被上传覆盖**（即使 `overwrite=true`），结论为参数错误 | 覆盖默认方案会把交付仓库改脏，也会悄悄改变所有人的默认行为 |
| 内容要求 | 内容里必须带**方案标识**（`scheme_id`），否则拒绝 | 没有标识的文件写进目录也列不出来，等于"传了但看不见"；当场说明比静默接受好 |
| 内容是否改写入库 | **完全不改写**用户内容（包括状态、标识） | 我们只做校验与落盘；若用户把上传件标成"随仓库交付的默认方案"，会在提醒里指出这会造成误导性标记，但不拦（"复制一份默认方案来改"是正常用法） |
| 已知限制 | ①上传时只能与"另一类的默认方案"配对校验，成对上传的两份自定义方案要到发起任务时才会一起被校验；②不检查方案标识是否与已登记方案重复 | 这是"先校验后落盘"在现有能力清单下的最稳做法；标识查重是否需要拦取决于前端是否用标识做键，留待对端确认 |
| 作业生效 | **同轮已让执行侧把本次选中的方案随作业分发**（否则上传的方案只在驱动端生效、作业仍按默认方案跑） | 见下方说明 |

补充一条与本轮相关的执行侧改动：此前集群作业固定读取随引擎包分发的仓库默认方案，导致"自定义方案"名不副实；本端在提交作业时改为分发**本次任务实际选中的方案文件**，并按它的文件名传给作业。旧的调用方式（不指定自定义方案）行为完全不变。
