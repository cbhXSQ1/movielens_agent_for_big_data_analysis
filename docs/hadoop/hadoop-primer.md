# Hadoop 零基础讲解：逻辑是承诺，物理是实现

> 面向：没学过 Hadoop 的团队成员（含汇报准备）
> 目标：理解 HDFS / MapReduce / YARN / Streaming 各自"负责什么、怎么做到"，以及我们的项目如何落在其中
> 读法约定：
> 1. 每个部分按同一顺序讲：**本职 → 没了它会怎样 → 怎么做（方式）→ 边界**
> 2. **【逻辑】**= 写代码、敲命令时看到的世界；**【物理】**= 机器上真实发生的事。两者分开讲，并用对照表配对
> 3. 术语先用白话说明"解决什么问题"，再给出专业名字

导航：① 四问 → ② HDFS → ③ MapReduce → ④ YARN → ⑤ Streaming → ⑥ 软件形态 → ⑦ 数据管道 → ⑧ 一次任务 → ⑨ 术语表 → ⑩ FAQ

## 一、四个问题，对应三个组件

我们的 ratings 文件 28MB，一台电脑随便处理。假设它是 28TB，会遇到四个问题：

| 问题 | 由谁回答 | 组件 |
|---|---|---|
| 数据放哪（一块硬盘装不下） | 把文件切开、分散到多台机器，还能当作一个文件用 | **HDFS** |
| 计算怎么拆（一台机器算不动） | 把程序拆小，分配到各台机器同时跑，再汇总 | **MapReduce** |
| 机器给谁用（多台机器怎么调度） | 把机器资源统一登记、统一分配 | **YARN** |
| 机器坏了怎么办 | 不单独设组件，而是三个组件各自内置容错 | （贯穿性设计） |

## 二、HDFS：负责"数据放哪"

**本职**：把一个大文件存到很多台机器的硬盘上，用起来却像只有一个文件；坏机器也不丢数据。

**没了它会怎样**：一个硬盘装不下 → 必须切开；切开散放 → 得记录"哪块在哪台机器"（这份记录后来叫**元数据**）；机器会坏 → 每块得存多份（每份叫**副本**）。

### 【逻辑】你使用时看到的 HDFS

和本地文件夹几乎一样：有目录、有文件路径；能上传、查看、删除、改名。你看到的 `ratings.dat` 是一个**整体文件**。

### 【物理】机器上真实发生的

1. 文件被切成固定大小的**块**（默认 128MB）。为什么定这个数：块太大 → 并行不起来；块太小 → "账本"条目太多，管不过来
2. 每块默认存 **3 份副本**，放在不同机器上
3. 有一台机器专门管账本（"哪个文件由哪些块组成、每块在哪几台机器"），它叫 **NameNode**；真正存数据的机器叫 **DataNode**
4. **上传**：客户端先问 NameNode"我往哪写" → NameNode 给一组 DataNode 地址 → 数据像接力一样一台传一台（每传一段有回执）→ 全部完成，NameNode 记账
5. **读取**：先问 NameNode"这些块在哪" → 客户端**直接**去最近的 DataNode 把各块读出来拼起来（不再经过 NameNode）
6. **保活**：每台 DataNode 每隔几秒向 NameNode"报平安"（这叫**心跳**）。长时间没心跳 → 认定它坏了 → 把它丢掉的副本从其他机器再复制一份，恢复到 3 份

### 逻辑 ↔ 物理 对照表

| 逻辑上你以为 | 物理上其实是 |
|---|---|
| 一个完整的文件 | 一堆块，分散在多台机器上 |
| 上传一个文件 | 客户端把各块流水线式推给多台机器 |
| 给文件改名 | 只改账本，一块数据都不搬（所以改名极快） |
| 删除文件 | 先删账本记录，数据块稍后慢慢清理 |

### 边界（它不负责的事）

- 不能在文件中间改写，只能追加 —— 它是为"批量处理"设计的，不是数据库
- 不适合海量小文件：每个文件在账本里都占位置，账本存在 NameNode 内存里，太多会撑爆
- 不做毫秒级查询

## 三、MapReduce：负责"计算怎么拆"

**本职**：把"处理海量数据"的程序拆成很多小份，分配到各台机器同时跑，再自动汇总成结果。

### 【逻辑】框架规定你只能写两个函数

- **map（一行数据）→ 若干（名字, 值）二元组**：处理原始材料
- **reduce（一个名字, 它的所有值）→ 结果**：处理"按名字归好类的一堆值"

小例子（数水果）：map 把每个水果变成 `(苹果, 1)`、`(香蕉, 1)`；reduce 对每个水果名把所有 1 加起来 → 得到每种水果的总数。这就是著名的 **WordCount**（数单词次数）的同一套路。所有 MapReduce 程序都要硬套进这两个函数——这么"不自由"，换来的是：框架可以自动把它并行到多台机器。

**框架对程序员的两个承诺（逻辑层的保证）**：

1. 你只管写函数，不用管数据在哪台机器
2. **同一个名字的所有值，一定会交给同一个 reduce 处理**

### 【物理】这两个函数在机器上真正怎么跑

按时间顺序：

1. **切**：文件按大小切成若干**分片**，一片对应一个 map 任务；调度时尽量让"存着这片数据的机器"来跑（省网络搬运）
2. **算**：map 进程逐行读、逐行产出二元组
3. **存中间结果**：产出先攒在内存里，攒满就写到**本机硬盘**的临时文件。写之前整理三件事：
   - **分区**：按"这个名字将来该交给哪个 reduce"分堆
   - **排序**：同一堆里按名字排好
   - **预合并**：先在本地把相同名字的合并一次（如 `(苹果,1)(苹果,1)` → `(苹果,2)`），减少后面要搬的数据量
4. **搬**：每个 reduce 任务去各台 map 机器"取自己该管的那堆数据"。这个网络搬运过程叫 **shuffle**，是整个流程最贵的一步
5. **归**：reduce 拿到的是按名字排好序的数据 → 同一个名字挨在一起 → 逐名字处理、输出
6. **写**：结果写回 HDFS；每个 reduce 产出一个 `part-00000` 这样的文件，全部成功再放一个 `_SUCCESS` 空标记文件

### 逻辑 ↔ 物理 对照表

| 逻辑承诺 | 物理实现手段 |
|---|---|
| "一份输入被并行处理" | 切成多个分片，每片一个独立进程 |
| "map 处理每一行" | 进程从分片文件里一行行读 |
| "同一名字的值会归到一起" | 分区 + 网络搬运（shuffle）+ 排序 |
| "reduce 收到一个名字和它所有的值" | reduce 顺序读已排序的数据，名字一变就换下一组 |
| "作业输出一个结果目录" | 每个 reduce 写一个 part 文件 + `_SUCCESS` 标记 |

### 容错（"机器坏了怎么办"的答案）

- 每个 map/reduce 都是独立进程：挂了 → 换一台机器重跑（输入还在 HDFS，能重新算）
- 有个别任务特别慢 → **推测执行**：在另一台机器同时跑第二份，谁先完成用谁
- 重跑可能产生重复输出 → 结果先写临时文件，成功才改成正式名字，失败的自动清理

### 边界

- 不适合"来回随机改数据"的场景（那是数据库/HBase 的活）
- 延迟高：一个作业光启动就要几十秒——它是为"吞吐量"设计的，不是为"快响应"

## 四、YARN：负责"机器资源怎么分配"

**本职**：把集群里所有机器的 CPU 和内存统一登记成一本账，谁要跑任务就来申请，用完归还。它不管数据、不管计算逻辑，只管"给机器"。

### 【逻辑】三个角色，各干一件事

| 角色 | 白话职责 |
|---|---|
| **ResourceManager**（总管，全局一个） | 手里只有一张账：每台机器还剩多少资源 |
| **NodeManager**（机器管家，每台一个） | 只管本机：我这儿在跑哪些任务 |
| **ApplicationMaster**（包工头，每个作业一个） | 替这一个作业去总管那要资源、安排活、盯进度 |

### 【物理】一个作业的申请流程

```
你提交作业 → 总管：找台机器先起"包工头"
包工头 → 总管：我要 5 个"运行名额"（一个名额=打包好的内存+CPU，叫容器）
总管 → 包工头：给你这几台
包工头 → 各机器管家：按名额启动任务进程（我们的 Python 脚本就在里面跑）
任务全完成 → 包工头汇报 → 作业结束，名额归还
```

**为什么把"资源"和"计算"分成两个系统**：这样同一套机器资源，MapReduce 能用、Spark 也能用——换计算框架不用换集群。

## 五、Hadoop Streaming：让 Python 程序"住进"MapReduce

**本职**：MapReduce 原生只认 Java。Streaming 是一个官方适配器，让"读一行、写一行的普通程序"直接充当 map 和 reduce。

### 【逻辑】协议（你和框架的约定）

- 当 map 用：从**标准输入**读一行 → 往**标准输出**写一行
- 当 reduce 用：一样，但收到的行已经"同键相邻、按键排好序"
- 行与"名字/值"的换算：一行的文本，用**第一个 Tab 键**分成"名字"和"值"（没有 Tab 就整行当名字）

### 【物理】运行方式

我们的脚本、配置文件、引擎打包（zip）会被复制到**每台要跑任务的机器**；然后每台机器上启动 Python 进程，喂给它对应分片的数据。map 脚本输出什么，Hadoop 就收集什么——后面全按第三部分的物理流程走。

## 六、Hadoop 本体的形态（回答"它是怎么实现的"）

- Hadoop 是一套 **Java 程序**（跑在 Java 虚拟机里）+ 一堆命令行工具，不是"一个软件"，而是**一组各司其职的常驻进程**
- **伪分布式**的含义：这组进程全都装在一台 Ubuntu 虚拟机里，互相通过本机地址通信。装完后 `jps` 能看到它们：

| 进程 | 是谁 |
|---|---|
| NameNode | HDFS 的账本管理员 |
| DataNode | HDFS 的数据存放员 |
| SecondaryNameNode | 帮 NameNode 定期整理账本（不是备用管理员） |
| ResourceManager | YARN 的资源总管 |
| NodeManager | YARN 的本机管家 |

- **完全分布式**只是把这些进程分到多台真机器上，别的机制完全一样
- 所谓"安装 Hadoop"，实际就是：装好 Java → 把程序放好 → 写几份配置文件（告诉这些进程彼此的地址、数据存哪个目录）→ 初始化账本 → 启动进程

## 七、正式的数据管道是怎么流动的

### 【逻辑】管道分五个"区"，各有各的本职

| 区 | 本职 | 铁律 |
|---|---|---|
| 原始区 | 存放刚进来的原始数据 | **永不修改**，出问题能回溯重算 |
| 加工区 | 清洗、修复、拼接的产物 | 每次加工"输入目录 → 输出目录"，可单独重跑 |
| 隔离区 | 判定有问题、先不放行的数据 | 每条记录保留"原样 + 哪条规则 + 原因" |
| 指标区 | 质量分数、命中统计 | 必须如实反映，不能占位 |
| 发布区 | 给下游（模型、前端、迭代二）使用的正式数据 | **只读、带版本、不覆盖** |

这些区不是机器上的特殊区域，就是 HDFS 上不同的目录。**生产的正式程度，取决于逻辑上的约定（谁可以写、谁只能读、能不能覆盖），而不是物理上有什么不同。**

### 【物理】每一趟处理的动作永远只有一种

读 HDFS → 起进程算 → 写 HDFS。所谓"数据管道"是**逻辑上的先后依赖**（A 作业的输出 = B 作业的输入，像流水线一样接起来，这叫 **DAG**，有向依赖图）。物理上没有一条"传送带"在自动流动，而是一趟趟作业接力跑。

## 八、把我们的一次任务串一遍

| 步骤 | 【逻辑】人看到的 | 【物理】机器上发生的 |
|---|---|---|
| 发起任务 | Agent 收到"请清洗评分并评估" | driver 先校验两份配置，然后依次提交作业 |
| 清洗（9 个作业） | "数据变干净了，坏的进隔离区" | 每个作业：总管起包工头 → 包工头要名额 → 各机器启动 Python 进程读 HDFS、写 HDFS |
| 评分（3 个作业） | "五维分数出来了，前后可对比" | 同样三趟作业：数数 → 汇总 → 算分，结果写回 HDFS |
| 发布 | "数据版本 v1 就绪" | 把产物复制到发布目录，比对内容指纹（哈希）确认没变 |
| Agent 展示 | 五维对比、数据量变化、异常样例 | Agent 读的是 driver 汇总好的 JSON 文件 |

## 九、术语小词典

| 术语 | 白话解释 |
|---|---|
| 元数据 | 记录"文件由哪些块组成、每块在哪台机器"的账本（不是数据本身） |
| 块 | 文件被切开后的一大段，默认 128MB |
| 副本 | 同一块多存几份，坏机器不丢数据 |
| 心跳 | DataNode 定期向 NameNode 报平安的信号 |
| 分片 | "一片交给一个 map 任务处理"的输入划分 |
| 键值对 | `(名字, 值)` 这样的二元组，MapReduce 的基本搬运单位 |
| 分区 | 决定"这个键将来去哪个 reduce" |
| 预合并 | map 端先把相同键合并一次，少搬数据 |
| shuffle | reduce 去各台机器把属于自己的数据搬回来的过程（最贵） |
| 容器 | 打包好的一份额度：多少内存 + 多少 CPU |
| 推测执行 | 慢任务在另一台机器并行跑第二份，谁快用谁 |
| DAG | 有先后依赖关系的作业图（A 的输出是 B 的输入） |

## 十、FAQ（答辩备用）

**Q1：为什么用 Python 写 map/reduce，不用 Java？**
Streaming 是 Hadoop 官方组件，专门为"用非 Java 语言写 map/reduce"设计，不损失 Hadoop 的任何核心机制（HDFS、YARN、shuffle、容错、计数器全部真实参与）。选择 Python 的原因：与 Agent 层同栈、开发与本地测试效率高、逻辑可复用于本地黄金测试。代价：每行数据的处理开销比 Java 略高——我们只有 100 万行，完全无感。

**Q2：一台机器也能叫 Hadoop 集群吗？**
我们用的是**伪分布式**：全部角色进程都在一台机器上，学到的机制与真实集群完全一致；完全分布式只是把进程分到多台机器，配置方式不同而已。

**Q3：为什么把清洗拆成十几个作业？**
MapReduce 单个作业的表达能力有限（基本是"一次遍历 + 一次按 key 汇总"）。把复杂逻辑拆成有先后依赖的作业图（DAG）是标准做法：每个作业"输入目录 → 输出目录"，可单独重跑、单独对账。

**Q4：100 万行有必要上 Hadoop 吗？**
单机当然也能做。本项目要求"清洗与评分实际通过 Hadoop 执行"，且我们的流程设计（原始区→隔离区→指标区→发布区、版本化、可回溯）与真实生产管道同构——这是课程考核的重点。
