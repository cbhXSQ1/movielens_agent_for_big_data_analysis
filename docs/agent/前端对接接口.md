# 前端对接接口说明（第 5 节 Agent → 第 6 节前端）

> 面向第 6 节（前端）同学。所有接口返回的都是**真实执行结果**，  
> 失败时返回真实原因，**不会给占位数字**。前端拿到什么就展示什么，不要自己造数。

---

## 一、三种对接方式，挑一个

| 方式                 | 适合                               | 怎么用                                              |
| ------------------ | -------------------------------- | ------------------------------------------------ |
| **① HTTP 服务（推荐）**  | 前端是网页 / 独立进程                     | `python3 -m agent.http_api --port 8765`，然后调 REST |
| ② Python 直接 import | 前端用 Python 写（Streamlit/Gradio 等） | `from agent import tools, explain`               |
| ③ 命令行              | 脚本 / 调试                          | `python3 -m agent.cli <工具>`，stdout 是一个 JSON      |

**推荐 ①**，前后端解耦，前端不用管 Hadoop 和 Python 环境怎么起。

```bash
cd ~/movieLens-agent
python3 -m agent.http_api --port 8765
```

已加 CORS 头（`Access-Control-Allow-Origin: *`），本地前端可直接跨域调。

### 接口清单（共 11 个）

| 方法   | 路径                                        | 说明                                          |
| ---- | ----------------------------------------- | ------------------------------------------- |
| GET  | `/health`                                 | 健康检查（**含 `llm.supported`，见 §九**）            |
| POST | **`/api/chat`**                           | ⭐ **前端主入口**：直接说人话，返回意图识别 + 结果（见 §二） |
| POST | `/api/tasks`                              | 发起任务，立即返回 task_id                          |
| POST | `/api/validate`                           | 校验清洗/评分方案是否合法（配置自检）                        |
| POST | `/api/llm/test`                           | 大模型可选层连通性自检（**未启用时后端返回 `LLM_UNSUPPORTED`**） |
| GET  | `/api/schemes`                            | 已登记方案列表                                     |
| GET  | `/api/tasks`                              | 最近任务列表                                      |
| GET  | `/api/tasks/{id}/status`                  | 查进度（**前端轮询这个**）                             |
| GET  | `/api/tasks/{id}/result`                  | 取最终结果（仅成功任务），加 `?explain=1` 附中文解释          |
| GET  | `/api/tasks/{id}/samples?type=&table=&n=` | 清洗后 / 隔离区样例                                 |
| GET  | `/api/tasks/{id}/report?format=md`        | 完整评估报告                                      |

> 11 个端点 = **8 个契约端点**（`/api/validate`、`/api/schemes`、`POST /api/tasks`、
> `GET /api/tasks`、`/status`、`/result`、`/samples`、`/report`）
> + **1 个 Agent 主入口**（`/api/chat`，内部按意图调上面的接口）+ **1 个健康检查**（`/health`）
> + **1 个大模型自检**（`/api/llm/test`，可选层，未启用时永远返回 `LLM_UNSUPPORTED`）。

## 二、`POST /api/chat` —— 前端主入口（一次提示闭环）

**前端默认走这个，不要走 `POST /api/tasks`。**

原因：迭代一要求「用户通过简易前端输入自然语言请求」「系统应理解用户目标」。
走 chat 才能拿到 `intent_cn`（系统自己说"我理解你要干什么"），
**证明意图是被识别的，而不是前端替用户选了个按钮**。走 tasks 就看不出这一层。

### 请求

```bash
curl -X POST http://localhost:8765/api/chat \
     -H 'Content-Type: application/json' \
     -d '{"text":"用默认规则清洗 MovieLens 1M 并评估五维质量", "exec_mode":"cluster"}'
```

| 字段 | 说明 |
|---|---|
| `text` | 用户原话（必填） |
| `task_id` | 可选。**追问时一定要带上**——后端靠它找回这一轮的运行口径（见 §二·五） |
| `auto_start` | 默认 `true`。识别为"发起清洗"时真提交任务；传 `false` 则只解析不提交 |
| `exec_mode` | `cluster`（默认，真 Hadoop）/ `local`（本地引擎，快）。会透传到 driver |
| `scope` | `full`（默认，全量正式口径）/ `sample`（评分表前 2000 行，**数字不可用于汇报**） |
| `rules` / `scoring` | 可选。自定义方案路径，不给就用已登记的默认方案 |
| `data_version` / `tag` | 可选。数据版本与任务备注 |
| `llm` | 可选。大模型配置对象 `{enabled, api_base, api_key, model}`，用于设置面板（见 §九） |

> 上面 6 个运行口径参数（`rules`/`scoring`/`data_version`/`tag`/`exec_mode`/`scope`）
> 只认这 6 个键，其它字段一律丢弃，不会透传给 driver。

### 返回

```json
{
  "ok": true,
  "intent": "clean_evaluate",
  "intent_cn": "发起清洗 + 五维评估任务",
  "reply": "任务已提交，ID：20260925-184303-379a4b\n它会依次完成：用户表清洗 → …",
  "data": {"ok": true, "task_id": "20260925-184303-379a4b", "status": "queued"},
  "task_id": "20260925-184303-379a4b",
  "task_started": true,
  "opts": {"exec_mode": "cluster", "scope": "full"},
  "engine": "rules",
  "llm": {"configured": false, "used": false, "note": ""}
}
```

比之前多了 4 个字段（都加在**外层**，`data` 结构不变，旧代码不受影响）：

| 字段 | 含义 | 前端怎么用 |
|---|---|---|
| `task_started` | 这一句是否真的发起了任务 | `true` 时才开始轮询进度 |
| `opts` | **本轮真实生效的运行口径** | 可直接回显；下次想显式回传就用这个值 |
| `engine` | `"rules"` = 规则解析 ／ `"llm"` = 大模型解析 | 建议显示在气泡上（如 `Agent · 规则解析`），如实交代 |
| `llm` | `{configured, used, note}` | `used=true` 时说明确实用到了；`note` 是回落原因，原样显示 |

### 二·五、会话级配置快照（**本次唯一的机制性变更，前端必读**）

**问题**：前端「追问」入口历史上只回传 `text` 和 `task_id`，
`exec_mode` / `scope` 全部丢失，driver 于是回落自己的默认值
（`cluster` + `full`），出现「页面上选的」和「实际跑的」不一致。

**修法**：后端按 **task_id** 记住这一轮真实生效的口径（`agent/session.py`）。
追问时只要带上 `task_id`，后端就自动取回那一次的口径——
**所以即使前端一个参数都不传，追问的口径也和第一次发起时一致**。

优先级：**本次请求显式传的 > 该 task_id 的快照 > driver 默认值**。

> 对前端的影响：
> - **不传任何参数也不会出错**（后端有兜底），但**强烈建议追问时带上 `task_id`**；
> - 想把口径显式传回来（例如页面做了「全量/样本」控件），直接传即可，会覆盖快照；
> - 后端把生效口径放在 `opts` 里回显，前端可以拿它做显示或下次回传。
>
> 进程重启后快照失效，回落到默认值（`cluster` + `full`）——失效方向是安全的。

`intent_cn` 建议**直接显示在页面上**（例如"已理解你的需求：发起清洗+五维评估任务"）。

### 支持的意图（`agent/intent.py` KEYWORDS 表，共 9 种 + 未识别）

| intent | `intent_cn`（页面直接显示这个） | 典型说法 |
|---|---|---|
| `clean_evaluate` | 发起清洗 + 五维评估任务 | "清洗并评估一下数据质量" |
| `task_status` | 查询任务执行进度 | "跑到哪一步了" |
| `task_result` | 获取任务结果（五维对比 / 数据量 / 隔离） | "结果出来了吗 / 多少分" |
| `get_samples` | 取样本（清洗后 / 隔离区） | "给我看 5 条被隔离的评分记录" |
| `get_report` | 获取完整评估报告 | "出一份完整报告" |
| `list_schemes` | 列出已登记方案 | "有哪些清洗方案" |
| `list_tasks` | 列出历史任务 | "之前跑过哪些任务" |
| `quick_demo` | 快速演示（不经 Hadoop） | "先快速演示一下" |
| `help` | 查看可用说法 | "你能干什么" |
| `unknown` | 未识别 | — `reply` 会列出可用说法，**不会瞎猜** |

> 有优先级：`quick_demo → get_samples → get_report → task_status → task_result
> → list_schemes → list_tasks → help → clean_evaluate`（先具体后笼统）。
> 想加说法只改 `agent/intent.py` 的 `KEYWORDS` 表即可。

⚠️ 注意：`/api/validate`（配置自检）**是一个 HTTP 端点，不是一种对话意图**——
用户不会用自然语言说"校验配置"，它是给前端做配置自检用的。

### `exec_mode` 与 `scope` 是真实生效的

`agent.py → tools.py → driver --exec <mode> --scope <scope>`，
前端的「Hadoop 集群 / 本地引擎」切换是真的传到 driver 的，**不是摆设**。

| 参数 | 取值 | 说明 |
|---|---|---|
| `exec_mode` | `cluster`（默认）/ `local` | `local` 不走 HDFS/YARN，快，但**不发布结果**（D-015） |
| `scope` | `full`（默认）/ `sample` | `sample` = 评分表前 **2000 行**，仅联调，**数字不可用于汇报** |

⚠️ 汇报用的数字必须来自 `cluster` + `full`，见 §六.3。
（`sample` 档是 2000 行，不是 400 行——如果听到"四百来份样本"的说法，以此处为准。）

## 三、直接发起任务（chat 之外的路径）

一般不用，前端若要手动控制提交流程再走这个。

### 发起任务

```bash
curl -X POST http://localhost:8765/api/tasks \
     -H 'Content-Type: application/json' \
     -d '{"exec_mode":"cluster","tag":"demo"}'
```

返回：

```json
{"ok": true, "task_id": "20260925-184303-379a4b", "status": "queued", "started_at": "..."}
```

> ⚠️ 全量集群跑约 **10 分钟**；演示想快可以传 `{"exec_mode":"local"}`（不走 HDFS/YARN，几分钟）。  
> 但**汇报用的数字必须来自 `cluster`**——`local` 模式**不会发布结果到 HDFS**
> （driver 决策 D-015：publish is cluster-only），本地引擎只用于快速演示。

### 查进度（每 3~5 秒轮询一次）

```bash
curl http://localhost:8765/api/tasks/20260925-184303-379a4b/status
```

```json
{
  "ok": true,
  "task_id": "20260925-184303-379a4b",
  "status": "running",
  "stage": "clean_ratings",
  "stage_index": 3,
  "stage_total": 9,
  "progress_percent": 33,
  "message": "running clean_ratings",
  "errors": []
}
```

- `status`：`queued` / `running` / `succeeded` / `failed`
- **阶段口径：`1 个起始状态 + 9 个工作阶段`。**
  完整序列是 `queued → clean_users → clean_movies → clean_ratings → stats_marks →
  score_before → score_after → finalize → publish → done`（共 10 项），
  但 `queued` 是"还没开始跑"的起始状态，不算工作阶段，
  所以 `stage_total` 返回 **9**，`stage_index` 取 1~9，`progress_percent = index / 9`。
- 9 个工作阶段：`clean_users → clean_movies → clean_ratings → stats_marks → score_before → score_after → finalize → publish → done`

> 📌 **口径澄清**：`docs/hadoop/agent-interface.md` §4.3 的示例里写的是 `"stage_total": 10`，
> 与 driver 实际返回值（9）不一致，属早期版本残留。**以接口实际返回为准**（前端按响应字段读，不受影响）。
> 已反馈给第 4 节，文档口径统一为「1 个起始状态 + 9 个工作阶段」。

### 取报告（⚠️ 默认值不一致，请显式传 `format`）

```bash
curl "http://localhost:8765/api/tasks/20260925-184303-379a4b/report?format=md"
```

| 位置 | 默认值 | 说明 |
|---|---|---|
| HTTP 接口 `agent/http_api.py:93` | **md** | 返回纯文本报告全文（`Content-Type: text/plain`） |
| driver CLI `run_task.py:569` | **json** | 返回 JSON 信封 |
| 契约文档 §4.7 示例 | 示例显式写了 `--format md` | 是示例，不代表默认值 |

**结论：三处不一致，前端请永远显式传 `format`**，别依赖默认值。
`format=json` 时 HTTP 也返回 JSON 信封（含 `report` 字段）。

## 四、前端要展示的四块内容

### 1）进度条

用 `status` 的 `progress_percent` + `message`。  
阶段名可以映射成中文：用户表清洗 / 电影表清洗 / 评分表清洗 / 统计打标 / 清洗前评分 / 清洗后评分 / 汇总 / 发布 / 完成。

### 2）五维对比（核心）

`GET /api/tasks/{id}/result` → `scores`：

```json
"scores": {
  "before": {"Accurate": 97.71, "Complete": 98.82, "Unique": 90.90,
             "Up-to-date": 98.22, "Consistent": 89.65, "composite": 95.07},
  "after":  {"Accurate": 99.79, "Complete": 99.99, "Unique": 100.0,
             "Up-to-date": 100.0, "Consistent": 100.0, "composite": 99.95},
  "delta":  {"Accurate": 2.08, "Complete": 1.17, "Unique": 9.10,
             "Up-to-date": 1.78, "Consistent": 10.35, "composite": 4.88}
}
```

建议做**雷达图或柱状对比图**（before / after 两组）。

### 3）数据量变化（必须同屏展示，不能只放分数）

`result.counts`：

```json
"counts": {
  "input":  {"ratings_lines": 1150241, "users_lines": 6946, "movies_lines": 4465},
  "output": {"ratings": 1000209, "users": 6040, "movies": 3883},
  "quarantine": {
    "total": 100830,
    "by_rule": {"R2": 43885, "R5": 12003, "X1": 10502, "X2": 10502, "P3": 7606,
                "R1": 6752, "P2": 6075, "R3": 3375, "U1": 72, "M1": 58}
  },
  "dedupe": {"ratings": 49510, "users": 726, "movies": 454},
  "fix":    {"R4_ms": 13503, "P1_text": 48, "M2_strip": 47, "U3_zip_plus4": 73}
}
```

### 4）局限性（必须展示）

`result.limitations` 是一个字符串数组，直接原样渲染：

```
- 用户属性为自愿填写、未经核验，A3/C1 不封顶是诚实口径
- U3/S4 等提升部分来自把无法判定的记录移出分母，而非真正修复，详见报告
- 时效性以数据集发布语境评估；以现实时间衡量必然过时
- 隔离数量只统计 action=quarantine 的规则；R6/M4/U5 属去重，单列于 counts.dedupe
```

### 5）两个加分字段（建议展示）

这两个字段是"系统主动说清楚"的体现，**展示出来比不展示加分**。

**① `GET /result?explain=1` → `_explanation`（中文长解释）**

就是在命令行看到的那一大段人话：`数据量变化 → 隔离/去重/修复 → 五维对比表 →
局限性与口径提醒`，四块**强制齐全**。
建议放在「总览」页最显眼的位置。

```bash
curl "http://localhost:8765/api/tasks/20260925-184303-379a4b/result?explain=1"
```

**② `result.rule_notes`（口径差异的主动披露）**

结构：`{"headline": "<口径说明>", "notes": [4 条]}`

含义（照抄 headline 的意思）：配置里的 `evidence` 字段是**人手写的测量备注，没有任何代码读它**，
引擎只执行 `detect`。本次有 **4 条规则**（U2 / U3 / M8 / R9）的 `evidence` 与它**自己那条**
`detect` 对不上，报告**一律以 `detect` 为准**，并**把两套数字并列**便于核对。
这 4 处**都不影响** counts 与 18 个指标值（已逐条验证）。

这是**系统自己暴露的问题**，不是被问出来的。
建议做成「评分依据」页底部一块，**有则显示、无则说明"本次没有"**。

> 展示这两条，等于向老师证明：**我们不怕暴露问题。**

## 六、三条必须遵守的约定（违反会扣分）

1. **不许造数**。任务没跑完就调 `result`，会返回：
   ```json
   {"ok": false, "error": {"code": "TASK_NOT_FINISHED", "message": "任务尚未完成（当前 running / clean_ratings）"}}
   ```
   前端此时应该**继续显示进度条**，绝对不能拿上一次的旧数字顶上。
2. **隔离 ≠ 修复**。展示分数提升时，必须同屏展示「数据量变化 + 隔离 100,830 行」。  
   只放一个"95.07 → 99.95"会被认为误导。
3. **权威结果以集群任务为准**。`quick_clean` 是附加的演示工具，数字同源但不维护任务状态，  
   不要拿它当正式结果展示。

## 七、错误码

| code                   | 含义          | 前端建议处理              |
| ---------------------- | ----------- | ------------------- |
| `TASK_NOT_FINISHED`    | 还在跑         | 继续轮询进度              |
| `TASK_FAILED`          | 跑失败         | 展示 `message` 里的真实原因 |
| `TASK_NOT_FOUND`       | task_id 不存在 | 提示重新发起              |
| `TASK_ALREADY_RUNNING` | 已有任务在跑      | 提示等待                |
| `CONFIG_INVALID`       | 配置非法        | 展示 `details`        |
| `USAGE`                | 参数错         | 检查参数                |
| `DRIVER_UNREACHABLE`   | driver 调不到  | 提示后端未启动             |

## 八、联调最小闭环

```bash
# 终端 1：起服务
python3 -m agent.http_api --port 8765

# 终端 2（推荐路径：走 chat，能拿到 intent_cn）
curl -X POST http://localhost:8765/api/chat \
     -H 'Content-Type: application/json' \
     -d '{"text":"任务 20260925-184303-379a4b 跑到哪一步了"}'

# 终端 2（直接调底层接口）
curl -X POST http://localhost:8765/api/tasks -H 'Content-Type: application/json' -d '{}'
curl http://localhost:8765/api/tasks/<id>/status
curl http://localhost:8765/api/tasks/<id>/result
```

已经跑成功的任务可以直接拿来联调（有真实数据，不用等 10 分钟）：

```
task_id = 20260925-184303-379a4b
```

用这个 task_id 做**追问类**演示是秒级的，适合现场展示"系统能听懂人话"。

## 九、大模型可选层（**默认关闭，没配就当它不存在**）

> 这一节是可选的。前端**不接也能 100% 正常工作**；
> 后端没启用时 `/health` 里 `llm.supported=false`，功能上 100% 走规则解析。
>
> ⚠️ **UI 口径（2026-09-29 与第 6 节定稿）**：`supported=false` 时**入口（齿轮）依然常显**，
> 点开面板给一句提示即可，**不要整块隐藏**——否则没配的机器上"做了等于白做"，
> 而且会出现"有无功能两套布局"。详见 §9.2。

### 9.1 它只做两件事

| ✅ 允许 | ❌ 绝不允许 |
|---|---|
| 把用户的话理解成系统调用（意图 + 参数） | 生成清洗规则（规则永远来自 `config/*.json`） |
| 把自述句说得更通顺（**措辞润色**） | 产出、修改、推测任何数字 |

**分数、行数、隔离数 100% 来自 Hadoop 的真实运行结果。**

### 9.2 前端怎么判断要不要显示设置入口

```bash
curl http://localhost:8765/health
```

```json
{"ok": true, "service": "agent-http-api/1.1", "scope_default": "full",
 "llm": {"supported": false, "configured": false}}
```

| 字段 | 含义 | 前端行为 |
|---|---|---|
| `llm.supported` | **后端总开关**（`AGENT_LLM_SUPPORTED`）开了没 | `false` → **齿轮照常显示**（常显，不隐藏），点开面板显示「后端未开启大模型增强：启动时设置 `AGENT_LLM_SUPPORTED=1`」 |
| `llm.configured` | 当前有没有真的配齐（enabled+base+key+model） | 只影响面板提示文案，不影响是否显示 |

> **默认 `supported=false`**：后端启动时没设 `AGENT_LLM_SUPPORTED=1` 就一直是 false。
> **入口始终可见**（避免"有无功能两套布局"，也让做好的面板不至于白做），
> 只是点开后提示未开启；此时所有请求一律走规则解析，不会发给大模型。
> 要演示就 `export AGENT_LLM_SUPPORTED=1` 后重启后端，面板即变为可用。
>
> 💡 `supported=false` 时点「测试连接」，后端直接返回
> `{"code":"LLM_DISABLED","message":"后端总开关未开：后端启动前需设置 AGENT_LLM_SUPPORTED=1"}`，
> 前端可直接用这条 message 当提示文案，无需自己写死。
>
> ⚠️ 这个总开关**不能由前端请求打开**（后端会剔除请求里的 `supported` 字段），
> 否则"默认关闭"这条承诺形同虚设。

### 9.3 配置怎么传

**只在单次请求里传，后端不落盘**（避免凭据进仓库）：

```json
{"text": "帮我看看进度",
 "llm": {"enabled": true, "api_base": "https://…/v1", "api_key": "sk-…", "model": "qwen-plus",
         "mode": "always"}}
```

**五项**（`enabled`/`api_base`/`api_key`/`model`/`mode`）缺任一项 = 不可用，
**自动回落规则解析，功能不降级**。（另有后端总开关 `AGENT_LLM_SUPPORTED`，见 §9.2。）

⚠️ **`mode` 一定要能选，而且演示要选 `always`**：

| mode | 什么时候去问大模型 | 说明 |
|---|---|---|
| `fallback`（默认） | **只有规则彻底听不懂（`unknown`）时才兜底问它** | 规则仍是主路径。常用说法规则都能识别（置信度 0.80~0.85），**所以现场很可能一次都不触发** |
| `always` | 每句都问一次 | **汇报现场演示用这个**，否则看不出效果 |

> 为什么不用"置信度阈值"：规则一旦命中关键词，置信度就 ≥0.8
> （`intent.py`：`0.5 + 0.15 × 命中词数`）。所以任何"低于阈值才去问"的写法
> 都是死条件——试过 0.5（永不触发）、0.8（0.80 不小于 0.8，还是不触发）。
> 与其留一个调了也没用的旋钮，不如把 `fallback` 的语义写死成"只在 unknown 时兜底"，
> 想演示就用 `always`。

`api_base` 填到 `/v1` 这一级即可。本地 Ollama 填 `http://localhost:11434/v1`、
`api_key` 随便填个非空值——**这是机房没网时唯一能演示大模型能力的配置**。

### 9.4 连通性自检

```bash
curl -X POST http://localhost:8765/api/llm/test -H 'Content-Type: application/json' \
     -d '{"llm":{"enabled":true,"api_base":"https://…/v1","api_key":"sk-…","model":"qwen-plus"}}'
```

```json
{"ok": true, "reachable": true, "latency_ms": 320,
 "config": {"model": "qwen-plus", "api_base": "https://…/v1", "mode": "fallback", …}}
```

⚠️ 返回里**不含 `api_key`**（后端已脱敏）。连不上时返回 `LLM_UNREACHABLE` 与真实原因。

### 9.5 什么时候会用到它

**默认 `fallback`：只有规则彻底听不懂（识别为 `unknown`）时才去问它**，
其余情况一律走规则——所以绝大多数交互是零延迟、零成本的。
（想要每句都问，用 `mode=always`，见 §9.3。）

`/api/chat` 返回里的三个字段如实交代了这一句到底是谁处理的：

| 场景 | `engine` | `llm.used` | `llm.note` |
|---|---|---|---|
| 没配大模型 | `rules` | `false` | 空 |
| 规则就识别出来了 | `rules` | `false` | 空 |
| 规则没把握，问了大模型且成功 | `llm` | `true` | 意图由大模型解析 |
| 问了但连不上 / 返回不合法 | `rules` | `false` | 「大模型不可用…已回落到规则解析：网络不可达：…」 |

**建议把 `engine` 显示在对话气泡上**（`规则解析` / `大模型解析`）——
这是最诚实、也最体现设计的做法，老师问"你们到底有没有接大模型"时一眼就能答。

### 9.6 三层护栏（答「它会不会编数字」）

1. **结构性隔离**：页面上所有数字都是 `explain` 模块拼出来的，
   那段文本**物理上根本不会传给大模型**；只有 4 类"无事实句"
   （任务已提交 / 没听懂 / 帮助语 / 只解析模式）允许润色。
2. **占位符模板**：润色前先把数字换成 `{v0} {v1}…`，它眼里没有数字；回来再回填原值。
3. **输出后校验**：占位符数量对不上 / 出现任何新数字 / 出现「修复了、已解决」这类措辞
   （隔离 ≠ 修复）/ 长度超标 —— **任一不过就丢弃润色，原样返回未润色文本**。
