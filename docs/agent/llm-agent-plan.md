# 第 5 节 Agent v2：LLM 主控改造计划

> 状态：方向已定；**阶段 0~5 全部完成（2026-09-30：网关验证 / 工具表 / 策略层 /
> LLM 循环 / /api/chat 接入 / 数字校验护栏；全量 379 测试绿 + 两路径端到端冒烟 PASS）**；
> 阶段 6（前端步骤流）按拍板 #6 列为可选（接口已留 `llm.steps` 加性字段）；
> driver 精细任务 v1.1（见 `docs/hadoop/driver-refactor-plan.md` 第 7 节）落地后
> 补工具表两项；真实网关多轮语义仍待 VM `--live` 补跑（见 gateway-probe.md §4）。
> 目标一句话：把"规则为主 + LLM 单步增强"改成 **LLM 主控的 function-calling 循环**；规则降为离线兜底与安全护栏。
> 总原则：对外接口加性变更、数字永远来自工具结果、LLM 不可用时回退规则路径、小步提交每步测试全绿。
> 结构原则：控制层是**跨步重构**——用新循环替换旧分派，不在 `respond()` 上继续加分支打补丁；补丁只允许用于独立缺陷修复。

## 1. 现状与差距（引用行号）

1. `agent/agent.py`：`respond()` 先跑规则解析（约 L106），LLM 只在门控通过时做一次"意图分类替换"（L118-136）；之后是 if/elif 分派（L155 起）；一条消息只调一个工具，**工具结果不回灌给模型**。
2. `agent/llm_client.py`：请求体只有 model 与 messages（L53-55），**不支持 tools / tool_calls**。
3. `agent/llm_parse.py`：白名单校验 `_sanitize`（L66-115）可作为工具参数校验的前身；`polish` 的数字遮罩护栏（L160-210）属于"润色器"时代的设计，循环模式下要换成"输出有据可查"。
4. `agent/session.py`：只存任务口径快照，没有对话历史。

## 2. 目标架构

三层，各管一件事：

```
LLM 循环（llm_loop）：对话历史 + 工具表 → 模型 → 工具调用 → 策略校验 → 执行 → 结果回灌 → 循环 → 基于结果的最终回答
策略层（tool_policy）：依赖、互斥/串行、前置条件、参数白名单、危险操作确认（CLI 与 HTTP 两条路径共用）
工具层（tool_specs）：现有工具 + driver v1.1 新命令，统一注册为 JSON Schema
```

关键约定：

- 模型只做两件事：选工具并填参数、拿到工具结果后组织回答。**回答里的每个数字必须能在本会话的工具返回里找到**（由校验器强制）。
- 工具执行仍是确定性代码（driver/Hadoop）；模型永远不生成清洗规则、不产出数字。
- 两条路径：LLM 可用走循环；不可用原样走现有规则路径（能力缩水但可用，离线演示不破）。

### 2.1 网关、协议与会话验证（第一个任务）

在写循环之前，先把"网关侧到底怎么用"验证清楚，三项做完再动代码。产出：探测脚本与结论写入 `docs/agent/gateway-probe.md`。

1. **协议探测**：给 opencode 代理（或直连 DeepSeek）发一版带 tools 的请求。
   - 返回 tool_calls：走原生协议。
   - 不支持：走严格 JSON 协议——模型每轮只输出 `{"action": "<工具名>", "args": {...}}` 或 `{"final": "<回答>"}`；代码解析执行，结果作为下一条消息回灌。
   - 两种协议只差解析层，循环、策略、工具表完全复用。
2. **会话 ID 适配验证**：确认网关的上下文机制——是每次调用无状态（我们每轮携带完整消息），还是网关要求会话标识（如 opencode 的会话 ID）。
   - 若需要会话 ID：做一个"会话 ID 转接头"，把 agent 的会话号/任务号映射为网关会话 ID；优先放在 `hadoop/tools/opencode_proxy.py`（网关代理侧统一处理），不要把网关细节渗进 agent 循环。
   - 验证多轮延续与并发任务下的会话隔离各一例。
3. **DeepSeek harness 现成插件评估**：找到并记录该插件的名称与来源，读清它负责哪一层（会话管理？工具调用适配？重试？），然后验证三件事：
   - 能不能装进我们的环境（依赖、版本、许可）；
   - 能不能被 `llm_client` 直接复用或部分借鉴；
   - 与我们自产循环是否冲突、维护成本多大。
   - 结论三选一：直接采用 / 借鉴其模式 / 不采用（写明理由）。

## 4. 分阶段任务（每步独立提交）

- 阶段 0：网关、协议与会话验证（见 2.1）。产物：探测脚本 + `docs/agent/gateway-probe.md`（协议、会话 ID、harness 插件三项结论与证据）。
- 阶段 1：工具表 `agent/tool_specs.py`。把上表翻译成 JSON Schema；先覆盖现有工具，新增两项等 driver v1.1 落地后补。单测校验 schema 形状、参数边界与现有一致。
- 阶段 2：策略层 `agent/tool_policy.py`。声明式策略表 + 校验器；单测覆盖每个工具的准入/拒绝、任务锁、依赖缺失、发布互斥。
- 阶段 3：LLM 循环 `agent/llm_loop.py`。历史装配、工具调用解析、策略校验、执行、回灌、限步限时；用 Mock 模型单测：多步序列、模型失败回退规则、策略拒绝后要求重规划。
- 阶段 4：接入 `agent/http_api.py` 的 /api/chat。LLM 可用走循环、不可用走规则；响应信封加 `llm.steps`（加性字段，旧前端忽略即可）。
- 阶段 5：护栏换代。回答数字校验器（必须能在本会话工具结果里找到）；`polish` 保留但只处理无数字自述句；单测：编造数字必被拦。
- 阶段 6（**已搁置**，2026-09-30 定）：前端显示执行步骤与"本次由 LLM 编排"标识。
  —— 第 6 节前端将整体重写，本项目不做该展示；`llm.steps` 接口保留在信封里
  （加性字段），展示形态由重写后的前端自行决定。

## 5. 验收标准

- 复合请求（"先清洗，再看看哪类问题最多，然后出报告"）能由循环多步完成。
- LLM 不可用时，同一句话回退规则路径：能完成的子集照常完成，不能的老实说没听懂。
- 编造数字的单测先红转绿（先证明能被拦下）。
- 旧契约测试全绿；前端不改也能用；离线演示路径可用。
- 每阶段：完整本地测试套件全绿 + Python 语法检查通过。
- **测试口径（省时）**：每步只跑本地单测与 Mock 测试；集群侧只用小样本（`--scope sample`）或复用已完成任务的结果；**全量集群端到端只在最终验收跑一次**，不做逐阶段全量。

## 6. 风险与回退

| 风险 | 对策 |
|---|---|
| 网关不支持 tools | 严格 JSON 协议（阶段 0 结论二选一） |
| 网关需要会话 ID | 阶段 0 做转接头（代理侧统一处理），验证多轮与并发隔离 |
| harness 插件不适合 | 阶段 0 给结论，不硬上；自产循环不依赖它 |
| 循环跑飞 | 限步（建议 6）、限时（建议 90 秒）、策略拒绝、最后回退规则路径 |
| 模型编造数字 | 输出校验器硬拦；数字只来自工具结果 |
| 对话历史过长 | 只保留最近 8 轮 + 任务口径快照（session 既有） |
| 敏感操作 | 策略层确认位，前端弹窗后续接 |

## 7. 代码风格（与 driver 同规）

- 方法名"动词 + 对象"，禁止 run、plan、do 单独出现；名词只留给数据类和属性。
- 不用 dataclass、类型注解、ABC、装饰器；普通类、`%` 格式化、显式循环；Python 3.8 兼容。
