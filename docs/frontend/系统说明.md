## 1. 本节负责什么

一句话：**用户说一句人话，界面把这件事的真实执行过程和真实结果如实展示出来。**

前端**不做任何数据加工**，也不自己判断数据质量：

| 层 | 谁负责 | 干什么 |
|---|---|---|
| 第 4 节 | `hadoop/` | 真正用 Hadoop Streaming 清洗数据、算五维分数 |
| 第 5 节 | `agent/` | 把用户的一句话解析成工具调用，把 JSON 结果翻成中文 |
| **第 6 节** | **`frontend/`（本节）** | **调接口、画界面、如实展示** |

前端与后端的全部交互只有一条通道：`agent/http_api.py` 提供的 HTTP 接口。

## 2. 技术选型与理由

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | **无**（原生 HTML / CSS / JavaScript） | 作业明确"不要求复杂的页面设计"；零构建意味着虚拟机里一条命令就能开，答辩时不用解释打包工具 |
| 依赖 | **零** | 目标运行环境（保险起见按完全离线设计），不引用任何 CDN 字体、图标库、图表库 |
| 图表 | **手写内联 SVG** | 雷达图、前后对比条、数据量条各约 40–60 行；无外部依赖，离线必定可用 |
| 构建 | **无** | 没有 `node_modules`，没有打包步骤，改完刷新即生效 |

## 3. 目录与文件职责

```
frontend/
├── index.html      页面结构：顶栏 + 左栏（对 Agent 说 / 执行情况 / 追问）+ 右栏五个视图
├── css/app.css     设计契约的全部 token 与组件样式
├── js/api.js       网络层：唯一出口，含错误码 → 中文映射
├── js/charts.js    图表层：手写 SVG 与数字格式化
├── js/scoring.js   「评分依据」页：读 config/*.json 渲染
├── js/app.js       状态机、轮询、全部渲染
└── README.md       运行方法与已知限制（面向开发者）
```

加载顺序（`index.html` 底部）：`api.js → charts.js → scoring.js → app.js`。
前三个只暴露命名空间（`ODAPI` / `ODCharts` / `ODFmt` / `ODScoring`），`app.js` 负责编排与 DOM 写入。

## 4. 运行方法

前端需要**同时**访问两个东西，因此要起两个服务。

### 4.1 起后端

```bash
cd <仓库根目录>
python -m agent.http_api --port 8765
```

### 4.2 起静态服务（**必须在仓库根目录**）

```bash
cd <仓库根目录>
python -m http.server 8080
```

浏览器访问：`http://localhost:8080/frontend/`

> **为什么必须在仓库根目录起？**
> 「评分依据」页要读 `../config/scoring_scheme.v1.json`。从仓库根起服务时，页面在 `/frontend/`、
> 配置在 `/config/`，属于同源，可以直接 fetch。这是"前端不硬编码规则"这条设计要求得以成立的前提。
> 若从 `frontend/` 目录起服务，页面会如实显示一条错误并给出正确启动方式，而不会退回硬编码。

### 4.3 换后端地址

只改 `js/api.js` 顶部的 `var API_BASE = 'http://localhost:8765';`（后端已开 CORS）。

## 5. 前端调用的接口清单

全部来自 `agent/http_api.py`（已逐个核对源码）。

| 方法 | 路径 | 前端用途 |
|---|---|---|
| GET | `/health` | 顶栏连接状态灯，每 15 秒轮询 |
| POST | `/api/chat` | **主入口**：一句人话 → 意图 + 中文回答 + 可选 task_id |
| GET | `/api/tasks/{id}/status` | 进度：`status / stage / stage_index / stage_total / progress_percent / errors` |
| GET | `/api/tasks/{id}/result?explain=1` | 权威结果 + Agent 中文说明（`_explanation`） |
| GET | `/api/tasks/{id}/samples?type=&table=&n=` | 清洗后 / 隔离区样例 |
| GET | `/api/tasks/{id}/report?format=md` | 评估报告全文（**纯文本**，不是 JSON） |
| GET | `/api/schemes` | 已登记方案列表 |
| GET | `/api/tasks` | 最近任务（Agent 追问时回退用） |
| POST | `/api/validate` | 预留 |
| GET | `../config/*.json` | 同源读取声明式配置（不属于 8765 接口） |

**为什么主入口用 `/api/chat` 而不是 `POST /api/tasks`**：
作业 §5 要求"一次提示即可发起完整任务"、"系统应理解用户目标"。
走 `/api/chat` 由 Agent 做意图解析，页面再展示它识别出的意图（`intent_cn`），
一次输入既能发起任务也能追问，且能当场证明"Agent 理解了目标"。

### 5.1 两个必须小心的接口行为（实测）

| 行为 | 说明 |
|---|---|
| 出错时 HTTP 状态码可能仍是 **200** | 必须判断响应体的 `ok` 字段，不能只看状态码 |
| `report?format=md` 返回 **纯文本** | 不是 JSON，解析方式与其他接口不同 |
| `/api/schemes` 的 `path` 在 Windows 上是**反斜杠** | `config\cleaning_rules.v1.json`，前端已做归一化 |

## 6. 页面结构与需求对应

### 6.1 顶栏
系统标题、数据版本、T1/T2 徽章、后端连接状态灯。
任务成功前，T1/T2 取自**已登记方案**（`config/cleaning_rules.v1.json` 的 `data_version.time_boundaries`）并标注来源；
任务成功后切换为**本次任务的实际值**（`result.time_boundaries`）。

### 6.2 左栏
1. **对 Agent 说**：自然语言输入框 + 5 个示例 chip + 执行方式选择（Hadoop 集群 / 本地引擎）
2. **执行情况**：9 阶段步进器 + 进度条 + 百分比 + 已用时；失败时给环节与原因
3. **追问 Agent**：对话区，回车发送，展示 `intent_cn` 与 `reply`

### 6.3 右栏五个视图

| 视图 | 内容 | 对应作业要求 |
|---|---|---|
| 总览 | Agent 对结果的说明、任务与版本元数据、综合分、数据量变化、评价局限 | Agent 解释 / 五维对比 |
| 五维对比 | 雷达图（前/后双多边形）、维度前后对比条、18 项指标明细 | 五维评分对比 |
| 清洗结果 | 输入→输出、**修复/去重/隔离三张独立卡片**、按规则命中排行、真实隔离记录 | 清洗结果 |
| 评分依据 | 五维定义、每个指标的说明/适用范围与局限/无法验证项、清洗规则清单、口径差异说明 | 评分依据 |
| 样例与报告 | 样例浏览器（类型×表×条数）、报告加载/复制/下载 | 结果获取 |

## 7. 三条设计红线如何落地

### 7.1 不编造
- 任务未成功时，右侧五个视图全部是"尚无结果"空态，**一个数字都不出现**。
- `/result` 在任务失败或未完成时按契约拒绝返回（`TASK_FAILED` / `TASK_NOT_FINISHED`），
  前端拿到错误信封后**只显示状态与原因**，绝不拿上一轮旧数字顶替。
- 指标明细里，某个指标本次没被度量时显示「**本次未产出**」而不是 0 分。
- 唯一的"示例数据"通路（`?demo=1`）在开发阶段就**被主动删除**了 —— 页面上不存在任何预置数字。

### 7.2 隔离 ≠ 修复
- 「清洗结果」页顶部常驻提示条：被隔离的记录是**移出正表**，不是被修好了。
- 修复 / 去重 / 隔离做成**三张独立卡片**，绝不合并成一个"已处理"数字。
- 分数与数据量变化始终同屏。

### 7.3 配置只读
- 「评分依据」页直接 `fetch` 两个配置文件渲染，**前端不硬编码任何规则、阈值、指标名或权重**；
  连 18 个指标的名称都是从 `scoring_scheme.v1.json` 查出来的。
- 清洗前后使用同一份评分方案，页面上展示两侧的 `sha256` 供核对。

## 8. 三个防翻车机制

| 机制 | 触发条件 | 作用 |
|---|---|---|
| **抽样警戒** | `counts.input.ratings_lines !== 1150241` | 顶部挂黄色持久横幅「抽样运行，数字不可用于汇报」 |
| **执行环境判定** | 结果里的 `paths.published_dir` 是否为 `null`（D-015 语义） | 全量 **且**经 Hadoop 执行 → 绿色「全量运行 · Hadoop 集群」；全量但走的是本地引擎 → 黄色「全量行数，但本次走的是本地引擎，不作为正式口径」。**只看行数不够** —— 本地引擎跑全量时行数一样是 1,150,241 |
| **快速预演标注** | Agent 意图为 `quick_demo` | 挂橙色横幅说明该路径**不经 Hadoop**、不维护任务状态，正式数字须用集群模式 |

这三条横幅都**不允许被永久关闭** —— 每次结果到达都会重新提示，避免"上次点了 ×，这次就不警告了"。

此外，刷页后现场不会丢：在追问里问一句「跑到哪一步了」，页面会**接管** Agent 返回的任务标识，
自动恢复进度、结果或失败原因。

## 9. 状态覆盖

按 craft 规则，每个面板都实现了五种形态：

| 形态 | 实现 |
|---|---|
| 加载 | 骨架屏（`skeleton`） |
| 空 | 标题 + 说明 + 下一步指引 |
| 错误 | 三要素：发生了什么 / 为什么 / 怎么办，并带重试入口 |
| 有数据 | 正常渲染 |
| 极端值 | 缺字段、空数组、超长原始行（等宽横向滚动）、缺失指标 → 均不崩 |

轮询失败采用指数退避（2s / 4s / 8s），连续 3 次失败后如实报错并给「重试查询」。

**渲染隔离**：结果页的 10 个区块逐块 `try/catch` 渲染。任一区块出错只在自身位置显示错误信息，
其余区块照常渲染 —— 不会因为一个区块的问题让整页变空白。

**图表层的可测试性**：`charts.js` 的三个绘图函数都是纯函数（数据进、SVG 字符串出），
不依赖 DOM，因此可以直接用真实结果数字在 Node 里断言输出（已如此验证）。

## 10. 设计契约

界面遵循 Open Design 设计系统 **`ibm`（IBM Carbon 风格）**。已落实到 `css/app.css` 的关键约束：

- **0 圆角**（按钮 / 输入框 / 卡片）；24px 胶囊仅用于 tag
- 卡片**无边框、无阴影**，层次靠背景色分层（`#ffffff → #f4f4f4 → #e0e0e0`）
- **唯一强调色** Blue 60 `#0f62fe`，同屏可见使用不超过 2 处（主按钮 + 进度条）
- 输入框**只有 2px 底边框**，不做四周描边
- 8px 栅格；字重仅 300 / 400 / 600（禁止 700）
- 禁用渐变、装饰性阴影、emoji 图标

另有一处**刻意的偏离并已注明**：契约给出的行高是拉丁口径（正文 1.50 / 标题 1.17），
中文按其渲染会出现多行字符上下相碰，因此正文用 **1.7**、标题用 **1.35**。这是 craft 规则中
明确的 CJK 覆盖项，优先级高于拉丁行高；契约的字号、字重、字距、颜色全部照用。

## 13. 已知限制（如实说明）

1. **没有取消按钮**：driver 与 Agent 都没有提供取消任务的接口。因此界面不画一个点了没用的按钮，
   改为明确显示进度与已用时，并在超过 1 分钟后提示"全量任务通常需要 8–10 分钟"。
2. **「本地引擎」不是正式口径**：它用同一套引擎在本地跑完清洗与评分，自第 4 节的 **D-015** 起
   **不再依赖 HDFS**（`publish()` 在非集群模式下是 no-op，`paths.published_dir` 为 `null`），
   因此在没有 Hadoop 的机器上也能成功 —— 这也让前端可以在 Windows 上完整验证成功路径。
   但课程要求「清洗与评分必须由 Hadoop 实际执行」，正式数字必须来自「Hadoop 集群」模式；
   页面依据**结果自带**的 `paths.published_dir` 判断执行环境（而不是界面上选中的执行方式 ——
   追问接管既有任务时，单选按钮与那个任务无关），用黄色/绿色横幅明确区分。
3. **字体回落**：契约指定 IBM Plex，本机通常未安装且不允许 CDN 字体，因此按契约声明的回退链
   落到 `Segoe UI / Microsoft YaHei`。
4. **自然语言解析是规则式的**（第 5 节实现）：覆盖常见说法，生僻说法会提示可用表达，不做猜测。
5. **单机伪分布式**：性能受限于单台虚拟机，架构可横向扩展但本轮未验证。

## 14. 口径协调与反馈闭环

开发过程中，前端以「实测 vs 文档」逐条比对，向对应负责人反馈了 7 处不一致，**全部已得到修复**：

| # | 前端实测到的问题 | 处理结果 |
|---|---|---|
| 1 | `前端对接接口.md` 的端点清单漏了 `POST /api/chat` 与 `POST /api/validate` | 已补齐，并把 `/api/chat` 标注为**前端主入口（一次提示闭环）** |
| 2 | `stage_total` 文档写 10，接口实测返回 9 | 已更正为 9，并说明「`queued` 是起始状态、不计入工作阶段」 |
| 3 | `report` 的默认格式在文档示例、driver CLI、HTTP 接口三处不一致 | 对接文档统一改为显式传参示例（前端本来两个格式都显式传参） |
| 4 | 「自然语言意图解析归第 5 节还是第 6 节」两份文档说法相反 | 已统一为「**解析归第 5 节**，第 6 节前端只负责展示 `intent_cn`，不做任何解析」 |
| 5 | `result.rule_notes`（口径差异主动披露）是文档外字段 | 已写入对接文档，前端做成「有则显示、无则说明本次没有」 |
| 6 | 任务失败时 `errors[].stage` 是空串，阶段名只在顶层 `stage` | 接口文档已澄清失败 `errors` 的实际形态；前端保留回退（`errors[].stage` 为空则用顶层 `stage`），两者不冲突 |
| 7 | 本地模式收尾仍依赖 `hdfs`，导致无 Hadoop 的机器上任务必然失败，前端无法验证成功路径 | 第 4 节以 **D-015** 修复：`publish()` 仅在集群模式生效，`paths.published_dir` 与 `status.published` 在本地模式为 `null`，并新增 4 个防回归测试 |

本节的实现一律**以源码与实测为准**；开发过程中**未改动他人任何文件**，问题均以「实测证据 + 复现步骤」的形式反馈。
